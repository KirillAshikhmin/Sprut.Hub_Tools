# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Назначение репозитория

Коллекция логических и глобальных сценариев для умного дома **Sprut.Hub**. Каждая папка верхнего уровня в CamelCase — отдельный сценарий (`VirtualThermostat`, `CircadianLight`, `RuntimeCounter` и т.д.). Сценарии импортируются и запускаются в самом хабе — здесь нет сборки, тестов через CI, package.json или линтера. Репозиторий — это исходники + документация.

## Среда выполнения и ограничения языка

Сценарии исполняются движком **Nashorn** внутри хаба. Это критическое ограничение, влияющее на каждую правку:

- Поддерживается **только ES5** плюс точечные возможности ES6: стрелочные функции, шаблонные строки, `const`/`let`, `Map`/`Set`, `for...of`.
- **Запрещено**: классы, модули (`import`/`export`), деструктуризация, промисы, `async`/`await`, spread/rest, `Object.assign` и прочий ES6+.
- Функции `trigger`/`compute`, несмотря на то что вызываются "асинхронно" хабом, пишутся как обычные синхронные функции — `async`/`await` нет.

Для асинхронных эффектов используются `setTimeout`/`setInterval`, `Cron`, подписки `Hub.subscribe(...)`.

## Два типа сценариев

В одной папке могут жить оба типа (например, `Battery/source/Global.js` + `Battery/source/Logic.js`, `TurnOffAllLight/source/MasterSwitch.js` (global) + `MasterSwitch.Logic.js`).

### Логический сценарий (`source/*.js`)

Реагирует на изменения характеристик конкретных устройств. Структура — см. `ScenarioTemplate/LogicScenarioTemplate.js` и `ScenarioTemplate/README.md`:

- Блок `info = { name, description, version, author, onStart, sourceServices, sourceCharacteristics, options, variables }` — **только метаданные**. Хаб читает `info` при загрузке/сохранении сценария. **Из кода в `info` обращаться нельзя**: значения опций и переменных там не будут обновляться. Все рабочие данные приходят аргументами в `trigger`/`compute`.
- `function trigger(source, value, variables, options, context)` — основная точка входа. При `onStart: true` вызывается также при запуске хаба и при каждом сохранении сценария.
- `function compute(source, value, variables, options, context)` — синхронный, возвращает значение, которое хаб запишет в характеристику. Использовать только при острой необходимости — выполняется синхронно и может затормозить хаб.
- `variables` — состояние сценария между вызовами; сбрасывается при перезагрузке хаба.

### Глобальный сценарий

Это **библиотека** функций/констант, доступная другим сценариям через `GlobalVariables.имя` или алиас `global.имя`. У него нет блока `info`, нет `trigger`/`compute` — просто набор функций верхнего уровня.

Жёсткие ограничения глобальных сценариев (не работают, если код вызван **из самого** глобального сценария напрямую; работают, если функция вызвана из логического/блочного сценария):
- нельзя изменять характеристики устройств;
- нельзя ставить таймеры/cron, которые вызывают этот же глобальный сценарий.

Практический вывод: глобальные сценарии — чистые утилиты. Управление устройствами и таймерами живёт в логических сценариях, которые вызывают глобальные функции.

## Типичная структура папки сценария

```
ИмяСценария/
  README.md                  # документация сценария (что делает, опции, переменные, ограничения)
  source/
    ИмяСценария.js           # логический и/или глобальный сценарий
  ИмяСценария.json           # экспорт сценария из UI хаба — НЕ редактировать
  .tests/
    config.json              # конфиг тестов (схема ScenarioSimulator)
    *.test.js                # тесты от спецификации README
    preset.json              # фикстуры для ручной проверки в веб-UI
```

Имена папок и `.js`-файлов — CamelCase. Допустимы исторические русские имена файлов (`Логический.js`, `Глобальный.js`) в существующих папках типа `CircadianLight/` — не переименовывать без причины.

Файлы README и комментарии в коде — на русском языке. Поля `name`/`desc` в опциях используют структуру `{ ru: "...", en: "..." }` для двуязычного UI.

### Обязательная пара: `.tests/` + `preset.json` для нового сценария

При создании любого нового сценария ВСЕГДА создаёшь:

1. **`.tests/config.json`** — со ссылкой на схему и логические/глобальные исходники.
2. **`.tests/*.test.js`** — тесты от README (см. §«Правила работы с тестами»).
3. **`.tests/preset.json`** — фикстура для ручной проверки сценария через веб-UI ScenarioSimulator. Описывает комнаты, аксессуары и сервисы, нужные для запуска. Один из аксессуаров помечается `"target": true` — тот, чьи характеристики триггерят `trigger(source, value, ...)` сценария (определяется по `info.sourceServices` / `info.sourceCharacteristics`).

Образец preset — `VirtualThermostat/.tests/preset.json`. Поля:

- `name`, `description` — для UI (русский).
- `options` — начальные значения опций сценария (имена из `info.options.*`).
- `variables` — обычно `{}`, инициализирует state.
- `rooms` — `[{"name":"..."}]`.
- `accessories[]` — `{ id, name, room, target?, services: [{ type, name?, characteristics: [{ type, value }] }] }`.
- Не указывай `time` — UI берёт реальное текущее.
- Типы сервисов/характеристик — `HS.*` / `HC.*` строки из `ScenarioTemplate/sh_types.json`.

Pre-flight перед коммитом сценария: проверь, что `.tests/preset.json` есть и `bun run cli serve` показывает сценарий в списке с рабочей ручной проверкой.

## Что нельзя редактировать или генерировать

- **`.json`-файлы сценариев в папках сценариев генерируются из `source/*.js` командой `./publish`** (см. раздел «Публикация сценария»). Вручную их НЕ редактировать — правки затрутся при следующей генерации. Источник правды — `source/*.js` + `publish.json`.
- Изменения, которые пользователь сделал вручную в коде, — не откатывать. Если видишь ошибку в его правке — указать на неё в тексте, а не "молча исправить".

## Источники истины по API

Когда нужны имена сервисов, характеристик, поведение API хаба:

- **`ScenarioTemplate/README.md`** — каноническое описание структуры сценариев и принципов кода ("Минимум кода, максимум читаемости. Читаемость в приоритете", SRP, DRY, KISS, ранние возвраты, без магических чисел).
- **`ScenarioTemplate/LogicScenarioTemplate.js`** — готовый шаблон логического сценария со всеми типами опций.
- **`ScenarioTemplate/spruthub.js`** — JS API хаба с TypeScript-объявлениями и русской документацией: `Hub`, `Accessory`, `Service`, `Characteristic`, `Cron`, `Notify`, `SSH`, `Mail`, `HttpClient`, `Utils`, `UtilsNet`, `setTimeout`/`setInterval`/`clear`, перечисления `HC` и `HS`.
- **`ScenarioTemplate/sh_types.json`** — полный список сервисов и характеристик с допустимыми форматами и значениями. Для промптов использовать сжатые версии: `prompt_optimized_types.txt` (95% сжатия) или `compressed_types.txt`. Скрипты сжатия (`compress_types.js`, `ultra_compact_types.js`, `prompt_optimized_types.js`) запускаются через `node <имя>.js`, см. `ScenarioTemplate/COMPRESSION_README.md`.

Структура устройства: **Аксессуар → Сервисы → Характеристики**. У сервиса каждый тип характеристики может быть только один; список разрешённых характеристик для типа сервиса задан в `sh_types.json`.

`source.getUUID()`: для аксессуара — `"123"`, для сервиса — `"123.45"`, для характеристики — `"123.45.67"`.

## Тестирование

Два подхода:

### Внешний тест-раннер `ScenarioSimulator/` (предпочтительный)

Эмулятор хаба + CLI + веб-UI. Тесты живут в `.tests/` рядом со сценарием, прогоняются на macOS/Linux/Windows без хаба.

```bash
cd ScenarioSimulator && bun install && bun run generate
bun run cli run TurnOffAllLight --root ..      # запуск тестов сценария
bun run cli serve --port 5173 --root ..         # веб-интерфейс
```

Полная документация — `ScenarioSimulator/README.md`. Формат конфига и DSL описаны там же.

#### Правила работы с тестами

1. **После любой правки сценария — прогнать тесты сценария**: `bun run cli run <Name> --root ..`. Перед коммитом — полный прогон `bun run cli run --root ..`. Все правки сценария должны оставлять тесты зелёными, иначе нужно либо чинить код, либо обновить тест (если правка меняет публичный контракт — тогда сначала обновляется README сценария, потом тест, потом код).
2. **Тесты пишутся ОТ СПЕЦИФИКАЦИИ (README/доки), а не от текущей реализации**. Каждый `describe` соответствует разделу README, каждый `it` — конкретному утверждению. Если тест проходит только потому что он повторяет логику реализации — он бесполезен. Тест должен падать, если код перестаёт делать то, что обещано в README.
3. **Полное покрытие пишется по принципу «чёрного ящика» через субагента**. Процесс: (а) составь словесную поведенческую спецификацию сценария — все параметры с дефолтами и диапазонами, тайминги, приоритеты правил, краевые случаи, явно перечисли неспецифицированные зоны; (б) поручи написание тестов субагенту, которому ЗАПРЕЩЕНО читать исходники сценария (`source/**`), его README и существующие `*.test.js` — только спецификация из задания и `ScenarioSimulator/README.md` (DSL); (в) субагент не подгоняет упавшие тесты под код: корректный падающий тест — это находка «спецификация↔код», он остаётся падающим и попадает в отчёт списком расхождений. Так тесты ловят реальные баги, а не подтверждают реализацию (пример: black-box набор `TurnOffAllLight/.tests/blackbox-*.test.js` нашёл, что `delayedDevices` при `delayedTurnOffTime: 0` молча не выключались никогда).
4. **Если тест упал — сначала разобраться, кто неправ**: код, README или сам тест. Не подгоняй тест под код "чтобы стало зелёным" — это маскирует реальные расхождения README↔код.
5. **Покрытие — отдельно global и logic части**. Если у сценария есть и `*.Global.js`, и `*.Logic.js`, для каждого свой `.test.js` файл (см. `TurnOffAllLight/.tests/master-switch-global.test.js` + `master-switch-logic.test.js`). Логический тестируется через `scenario.run({source, value, variables, options, context})`; глобальный — через `scenario.call(name, args)` либо через подмену `variables.global.X = spy`.
6. **Тесты — артефакт первого класса, поддерживай в актуальном состоянии**. При добавлении опции в сценарий — добавь тесты на её работу. При удалении — удали соответствующие тесты. README, код, тесты должны быть синхронны.

### Старый подход через `UnitTest/source/UnitTests.js` (поддерживается)

Прогон внутри хаба, тесты встроены в сценарий:

- Скопировать функцию `runTests` (и нужные `assert*`) в свой сценарий и вызвать в `trigger`. При `onStart: true` `trigger` вызывается на каждом сохранении сценария — это и есть прогон тестов.
- Для тестов без реальных устройств — мок-объекты через `createUnitTestFullAccessory`/`createUnitTestAccessory`/`createUnitTestService`/`createUnitTestCharacteristic`. Возвращают объекты, совместимые по API с настоящими `Accessory`/`Service`/`Characteristic`.

Новые сценарии лучше тестировать через `ScenarioSimulator/`, существующие тесты можно мигрировать командой `scenario-sim migrate <scenario>`.

## README сценария — обязательные разделы

Когда пишешь или правишь `README.md` сценария — должно быть:
- назначение и поведение;
- ключевые опции (`options`) и переменные (`variables`) с объяснением каждого поля;
- особенности настройки в UI Sprut.Hub;
- известные ограничения и важные замечания.

## Публикация сценария (`./publish`)

Команда готовит сценарий к публикации из его исходников:

```bash
./publish <ИмяПапкиСценария>                 # полный прогон: проверки -> генерация JSON -> тесты -> архив
./publish <Имя> --check                       # только проверки + diff, без записи
./publish <Имя> --init                        # только (пере)создать publish.json
./publish <Имя> --no-tests                    # пропустить тесты
./publish <Имя> --allow-missing-changelog     # отсутствие записи в changelog -> предупреждение
```

Модель: сначала выполняются ВСЕ проверки (синтаксис и неподдерживаемые в Nashorn конструкции, метаданные `info`, наличие записи в README «История изменений» для текущей версии, коллизии/сироты JSON, дрейф версии, тесты симулятора). Если есть хотя бы одна ошибка — печатается весь список, на диск ничего не пишется. Если ошибок нет — генерируются `.json`, при отсутствии — `publish.json`, и собирается zip-архив.

### Манифест `publish.json`

Лежит в корне папки сценария. Описывает соответствие `source/*.js` → выходной JSON и метаданные глобальных сценариев (у них нет блока `info`). Если файла нет — создаётся автоматически при первом запуске (проверьте результат). Полная схема — `ScenarioSimulator/schemas/publish.schema.json`. Ключевые поля: `files[].source` (обязательно), `files[].json`, `files[].name` (для GLOBAL), `files[].primary` (какой логический файл даёт версию для changelog), `files[].archive` и верхнеуровневый `archive` (имя zip или `true`).

Версия для проверки changelog берётся из `info.version` логического файла (при нескольких — из помеченного `primary`), а `publish.json`→`version` используется как запасной вариант для чисто глобальных пакетов.

## Как здесь работает Autopilot

Отдельные сценарии собираются навыком `/autopilot`. Требования, спецификация и таски
конкретной сборки — в `.autopilot/<слаг>/`. Прогресс — `.autopilot/dashboard.html`.
Правило: требование из `manifest.md` может снять только пользователь.

Если сборка прервалась — скажи «продолжи автопилот»: состояние поднимется
из `.autopilot/state.js`, переспрашивать ничего не нужно.

### Найдено по ходу сборок

- Проверить синтаксис сценария настоящим Nashorn, не дожидаясь хаба:
  `/opt/homebrew/opt/openjdk@11/bin/jjs -scripting --language=es6 -co <файл>`.
  Флага `-c` у `jjs` нет — компиляция без запуска это `-co`. В JDK 15+ Nashorn удалён.
- Java-методы в Nashorn нельзя вызывать через `.apply`/`.call` — массив передаётся прямо в varargs.
- Эталон для нового сценария — `MotionLightAutomation/`: структура, подписки, логирование,
  `collectServicesByTypes` копируются оттуда, сам эталон не правится.
- `publish.json`: поле `archive` ставят только многофайловые пакеты (`Battery`,
  `CircadianLight`, `TurnOffAllLight`); однофайловый LOGIC его не ставит.
- Стенд ScenarioSimulator: собственная запись сценария в привязанную характеристику **не**
  вызывает повторный `trigger` (реальный хаб вызывает) — внешнее изменение эмулируется
  записью значения плюс повторным `scenario.run`.
- Числовые значения характеристик стенд приводит к `minValue`/`maxValue` до вызова сценария
  (`ScenarioSimulator/packages/core/src/metadata/ValueCoercer.ts`), поэтому тест
  «значение вне диапазона» недостижим.
- `service.getName()` возвращает **Java-строку**: сравнение с JS-строкой напрямую всегда ложно.
  Гард «не писать то же имя» без `String(service.getName()) === name` молча мёртв на хабе,
  при этом тесты на стенде зелёные.
- Поколение таймера (`global["<Префикс>_gen_" + uuid]`) поднимается **до** проверки настроек,
  а не после. Ранний выход по ошибке валидации не гасит колбэк прошлого экземпляра, и после
  пересохранения со сломанными параметрами устройством продолжает управлять старый таймер.
- Стенд: `time.set(iso)` только переставляет часы (`TimeController.setNow`) и **не** выполняет
  висящие таймеры — их выполняют `time.advance` / `time.tick` / `time.runAllTimers()`. Поэтому
  дату теста ставят до первого `scenario.run`.
- Стенд: `char.setValueSilent(v)` меняет значение характеристики, не вызывая подписки — так
  эмулируется «значение изменилось снаружи, а `trigger` не вызывался» (путь «пересчёт по таймеру»).

### Сценарий `ExhaustFanAutomation/`

Вытяжка по присутствию и влажности: включение по накопленному присутствию, выключение после
ухода с досушкой до рабочего порога, предельное время работы, ручные входы и «рубильник».
Единственный исходник — `ExhaustFanAutomation/source/ExhaustFanAutomation.js`.
Поведенческая спецификация — `ExhaustFanAutomation/.tests/SPEC.md` (§1…§19; §17 открытые
вопросы, §18 неспецифицированные зоны, §19 соглашения стенда), каждый black-box тест
ссылается на номер её раздела.

Решения, которые не надо переоткрывать:

- Поколения подписок живут в `global["EFA_subGen_" + uuid]`: при пересохранении сценария хаб
  запускает скрипт заново, но старый колбэк остаётся жив со старым `variables`. В отличие от
  эталона защита распространена и на таймеры — все `setTimeout` идут через
  `scheduleGuardedTimeout`, потому что предельный таймер живёт до 180 минут и переживёт
  пересохранение.
- Стартовый вызов `trigger` (`onStart`) отличается только по `!variables.externalSubscribed` —
  отдельного признака хаб не даёт; на старте нельзя ставить ни ручное удержание, ни блокировку.
- `PRESENCE_READY_TOLERANCE_MS = 50`: таймер накопления присутствия срабатывает на доли
  миллисекунды раньше расчётного момента, без допуска включение молча теряется до следующего
  события датчика.
- `DEBOUNCE_MANUAL_AFTER_SENSOR_MS = 5000` гасит ложные кнопку/импульс/контакт сразу после
  авто-включения по датчику.
- Блокировка авто-включения одна (`variables.autoOnLock`) на две причины, `manualOff` и
  `maxRun`: снимаются они в один и тот же момент «вытяжка погасла бы сама» — тишина дольше
  `offDelaySeconds` плюс влажность в норме; различаются только текстом в логе.

### Сценарий `SunInWindow/`

Флаг «Солнце светит в это окно»: положение Солнца считается на текущий момент, сравнивается с
направлением окна (румб или точный азимут) и двумя порогами — высотой над горизонтом и
отклонением от направления окна. Единственный исходник —
`SunInWindow/source/SunInWindow.js`, глобальной части нет (`scenario.call` неприменим).
Поведенческая спецификация — `SunInWindow/.tests/SPEC.md` (§1…§18; §17 неспецифицированные
зоны, §18 соглашения стенда), каждый тест в `.tests/blackbox-logic.test.js` ссылается на
номер её раздела.

Решения, которые не надо переоткрывать:

- Астрономия считается в UTC от абсолютного момента (`date.getTime()`): часовой пояс хаба в
  расчёт не входит и испортить его не может. Уравнение времени отдельно не считается — оно уже
  сидит в разнице между звёздным временем Гринвича и прямым восхождением. Следствие для опор в
  тестах: круглый час не является солнечным полднем (на экваторе в равноденствие 12:00 UTC даёт
  88,17°, а не 90°), поэтому опоры берутся на истинный солнечный полдень.
- `AZIMUTH_NOT_SET = -1` — сентинел «точный азимут не задан»: 0 это законный Север, поэтому
  «пусто» пришлось вынести за рабочий диапазон 0…360. Все пустые формы из формы хаба (`-1`,
  `null`, `undefined`, `""`, `"   "`) значат одно и то же и ошибкой не являются; ошибка — только
  непустое неразбираемое значение или число вне 0…360, включая `-0.5`.
- Проверяемые параметры дефолтом не подменяются: нечисловое значение доходит до
  `validateSettings` как `NaN` и останавливает сценарий. Тихая подстановка Юга или другого
  порога дала бы молча неверный ответ вместо явной ошибки. Румб проверяется по списку восьми
  значений (`listError`), а не по диапазону, и проверяется всегда — даже когда направление
  всё равно берётся из точного азимута.
- Зажимается ровно один параметр — `updateInterval` (1…60 минут): неверный интервал не повод
  перестать отвечать на вопрос «светит ли Солнце», в отличие от неверных координат, при которых
  ответа просто нет.
- При ошибке настроек характеристика не трогается вообще и таймер не ставится: снятый флаг
  означал бы «солнца в окне нет», а правда в том, что сценарий не знает ответа.
- Поколения таймеров — `global["SIW_gen_" + UUID сервиса]` (ключ по сервису, чтобы экземпляры
  на разных окнах не гасили таймеры друг друга), планировщик — рекурсивный `setTimeout`, а не
  `setInterval`: старый цикл гасит себя сам, увидев чужой номер. Недоступный `global` работу не
  останавливает (лишний таймер лучше отказа считать), но строка об утрате защиты пишется — один
  раз на запуск скрипта, через модульный флаг `generationProtectionReported`, а не через
  `variables`: те пересоздаются, и минутный таймер залил бы журнал.
- Ручное удержание не переживает перезапуск и пересохранение: признак свежего экземпляра —
  `!variables.initialState`, и вместе с `HUB[OnStart]` в `context` он заставляет записать
  расчётное состояние независимо от `allowManualControl`. Отдельного признака хаб не даёт.
- Ни то же значение характеристики, ни то же имя сервиса повторно не пишутся, и лог идёт только
  на смене состояния: при выключенном ручном управлении сюда заходит каждый тик минутного
  таймера. Имя сервиса отражает положение Солнца, а не записанное значение — при `invert` оно
  остаётся правдивым.
- `HC.Active` в `sourceCharacteristics` не объявлять: у `Switch`, `Outlet` и `Lightbulb` такой
  характеристики нет, это была бы точка привязки, которой не существует.
