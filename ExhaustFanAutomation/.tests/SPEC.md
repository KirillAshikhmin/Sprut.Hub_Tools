## 1. Файлы сценария

| Файл | Роль | Комментарий |
|---|---|---|
| `source/ExhaustFanAutomation.js` | **LOGIC** | Единственный файл. Содержит блок `info` (`name`, `description`, `version`, `author`, `onStart: true`, `sourceServices`, `sourceCharacteristics`, `options`, `variables`) и функцию `trigger(source, value, variables, options, context)`. Функция `compute` не объявлена: сценарий не вычисляет значение характеристики, а реагирует на события (проверяется отсутствием имени `compute` в контексте, а не вызовом). |

## 2. Назначение и общая модель

Сценарий привязывается ровно к **одному** сервису вытяжки — `Switch`, `FanBasic` или `Fan` —
и управляет её состоянием «включена/выключена». Он включает вытяжку, когда в комнате
кто-то задержался, продолжает работу, пока не упадёт влажность, ориентируется на «сухую»
комнату через контрольный датчик, и в любом случае выключается не позже заданного предела.
Ручное управление и «рубильник» автоматики устроены как в эталонном `MotionLightAutomation`.

### Терминология

- **Вытяжка / привязанный сервис** — сервис `Switch`/`FanBasic` (характеристика `On`) либо
  `Fan` (характеристика `Active`, `1` = включена, `0` = выключена), к которому привязан
  данный экземпляр сценария.
- **Датчик активности** — устройство из слота `motion1`/`motion2`/`motion3`.
- **Активность датчиков (occupancy)** — истинна, если активен хотя бы один настроенный слот.
- **Сессия присутствия** — непрерывный (с допуском, §6) период активности, по длительности
  которого принимается решение о включении.
- **Ручной вход** — устройство из слота `manualControl1..3`.
- **Внешнее изменение** — включение/выключение самого привязанного сервиса не сценарием:
  приложение, сцена, голос, физическая кнопка на вытяжке.
- **Рабочий порог влажности** — вычисляемый порог выключения (§7), он же база для «высокой
  влажности».

## 3. Триггеры

### 3.1 Основной триггер (привязка)

- `sourceServices`: `Switch`, `FanBasic`, `Fan`. `Outlet` намеренно не входит.
- `sourceCharacteristics`: `On`, `Active`.
- `onStart: true` — `trigger` вызывается: (а) при запуске хаба; (б) при каждом сохранении
  сценария; (в) при каждом изменении `On`/`Active` привязанного сервиса, кем бы оно ни было
  сделано.
- Значение (`value`) нормализуется: включено = `value === true || value === 1`.

### 3.2 Отслеживаемые события (подписки)

Сценарий подписывается на типы `MotionSensor`, `OccupancySensor`, `ContactSensor`,
`HumiditySensor`, `Switch`, `StatelessProgrammableSwitch`, `C_PulseMeter` и характеристики
`MotionDetected`, `OccupancyDetected`, `ContactSensorState`, `CurrentRelativeHumidity`, `On`,
`ProgrammableSwitchEvent`, `C_PulseCount`.

Событие учитывается, **только если UUID сервиса совпадает с одним из выбранных в опциях**;
совпадения по типу недостаточно. Подписки активны с первого вызова `trigger` (гарантирован
`onStart: true`).

### 3.3 Активные значения датчиков активности

- `MotionDetected`: активно = `true`.
- `OccupancyDetected`: активно = `1`.
- `ContactSensorState`: активно = `1` («Открыто»); при `contactInverted: true` — `0` («Закрыто»).

### 3.4 Значения ручных входов

- `Switch.On` — вытяжка повторяет состояние (не toggle).
- `ContactSensor.ContactSensorState` — только `1` переключает; `0` игнорируется.
- `StatelessProgrammableSwitch.ProgrammableSwitchEvent` — только `0` («одиночное») переключает;
  `1`/`2` игнорируются.
- `C_PulseMeter.C_PulseCount` — любое значение `> 0` переключает; `0` игнорируется.

## 5. Состояние между вызовами (`variables`)

Сценарий хранит в `variables`: момент начала сессии присутствия, идентификаторы таймеров
включения / сброса сессии / выключения / предела, момент включения (`runStartedAt`), момент
последнего авто-включения (для антидребезга), признак ручного удержания, признак блокировки
после ручного выключения, признак блокировки после предельного таймера, конец паузы
(`cooldownUntil`). Всё это сбрасывается при перезапуске хаба и при сохранении сценария;
поведение после сброса описано в §14.

Конкретные имена полей `variables` — деталь реализации и тестами не проверяются
(кроме наблюдаемых через поведение эффектов).

## 6. Присутствие и накопление сессии

- `computeOccupancyActive()` истинна, если активен хотя бы один из **заполненных** слотов
  `motion1..3`. Если не заполнен ни один — активность всегда ложна (сценарий живёт на
  влажности и ручных входах).
- Появилась активность → если сессия ещё не начата, она начинается «сейчас» и заводится
  таймер включения на `onDelaySeconds`; если был заведён таймер сброса сессии — он снимается.
- Пропала активность (все датчики неактивны) → заводится таймер сброса сессии на
  `offDelaySeconds`.
- Сработал таймер сброса сессии → сессия обнуляется, таймер включения снимается: следующий
  отсчёт `onDelaySeconds` начнётся с нуля.
- Сработал таймер включения → попытка авто-включения (§8).
- `onDelaySeconds: 0` → включение при первой же активности, без накопления.
- **Допуск**: провал активности короче `offDelaySeconds` сессию не обрывает и отсчёт
  `onDelaySeconds` не сбрасывает.

## 7. Влажность

- Чтение датчика даёт число либо «нет значения» (сервис не выбран, не найден, значение не
  число).
- **Рабочий порог** = `targetHumidity`, если контрольный датчик не выбран, не читается или
  его значение строго меньше `targetHumidity`; иначе `min(100, контрольный + referenceDelta)`.
- Порог нигде не кэшируется: он пересчитывается при каждой проверке. Проверка запускается
  по событию `CurrentRelativeHumidity` **любого** из двух датчиков (комнатного и контрольного),
  при включении, при срабатывании таймера выключения и предельного таймера. Событие
  контрольного датчика делает то же, что событие комнатного: переоценивает выключение (§10)
  и скорость (§9).
- **Условие по влажности выполнено** (`isHumiditySatisfied`), если: датчик влажности не выбран
  **или** его значение не читается (мёртвый датчик) **или** значение ≤ рабочего порога.
- **Высокая влажность** (`isHumidityHigh`): значение комнатного датчика ≥ рабочий порог +
  `humidityHighDelta`. Одно понятие обслуживает и включение по влажности (§8), и форсаж (§9).

## 8. Авто-включение

Выполняется, если **все** условия истинны:

1. автоматика разрешена (§11);
2. вытяжка выключена;
3. не идёт пауза после авто-выключения (`cooldownMinutes`, §10);
4. не стоит блокировка «не включать после ручного выключения» (§12);
5. не стоит блокировка после предельного таймера (§10);
6. есть повод: сработал таймер накопления присутствия (§6) **или** высокая влажность (§7)
   при включённой `humidityStartsFan`.

При включении: записать «включено» в привязанный сервис, запомнить момент включения, завести
предельный таймер, применить скорость (§9), запомнить момент авто-включения для антидребезга
(§12). Если в момент включения активности датчиков нет (включение по влажности или ручное) —
таймер выключения заводится сразу.

## 9. Скорость (форсаж)

- Действует, только если `boostEnabled: true` **и** у привязанного сервиса есть `RotationSpeed`.
- Пока влажность высокая (§7) — пишется `boostSpeed`, иначе — `normalSpeed`.
- Пересчёт при включении и при каждом событии любого из двух датчиков влажности.
- Если характеристики `RotationSpeed` нет — опция не действует, сценарий работает штатно.
- Скорость никогда не пишется, пока вытяжка выключена.

## 10. Авто-выключение, предел, пауза

**Обычное авто-выключение** выполняется, когда **все** условия истинны:

- все датчики неактивны дольше `offDelaySeconds`;
- условие по влажности выполнено (§7);
- прошло `minRunMinutes` с момента включения (`0` — проверка отключена);
- ни один ручной `Switch` не в `On` (§12);
- не поднято ручное удержание (§12).

Отсчёт `offDelaySeconds` начинается в момент потери последней активности; возврат активности
до истечения отменяет отсчёт (досушка продолжается, §7), при этом предельный таймер **не**
сбрасывается.

**Предельный таймер** (`maxRunMinutes`, `0` = выкл) отсчитывается от момента включения.
Срабатывание выключает вытяжку, **не** проверяя влажность, присутствие и минимальное время.
Единственное исключение — ручной `Switch` в `On`. Предел действует на любое включение:
по присутствию, по влажности и ручное.

**Блокировка после предела**: сразу после выключения по пределу авто-включение запрещено,
пока повод не исчезнет естественным путём — нет активности дольше `offDelaySeconds`
**и** условие по влажности выполнено. Ручное включение блокировку снимает.

**Уведомление**: при срабатывании предельного таймера, если `notifyOnDryTimeout` включено,
датчик влажности выбран и его значение выше рабочего порога — сценарий пишет одно сообщение
о недосушке. Доставка **только** `log.message(...)`: одна запись на один повод. Опции выбора
получателей и режима доставки у сценария нет, вариантов оформления — тоже один.

Сообщение несёт факты: влажность, рабочий порог (`computeEffectiveTarget` из §7, а не значение
опции `targetHumidity` — при контрольном датчике они расходятся), сколько вытяжка отработала,
устройство с идентификатором и комнату. Точные формулировки — вне контракта (§17.6).

**Пауза** (`cooldownMinutes`, `0` = выкл): после **авто**-выключения по таймеру (не по пределу)
в течение паузы авто-включение не выполняется. Ручное включение работает. **По истечении паузы
сценарий сам проверяет, есть ли повод работать (§8), и включает вытяжку — нового события датчика
для этого не требуется.** Смысл паузы — переждать и продолжить, а не отменить повод; блокировка
после предела (выше) устроена обратным образом: её снимает только естественное исчезновение повода.

## 11. Разрешение автоматики («рубильник»)

- `gateAutoSwitch` пуст → автоматика разрешена всегда.
- Иначе разрешение = значение выключателя, а при `gateAutoSwitchInvert: true` — его отрицание.
- Пока автоматика запрещена: авто-включение не выполняется; уже работающая вытяжка **не**
  гасится; таймеры продолжают работать.
- Переход выключателя в «разрешено» при активных датчиках — повод попробовать авто-включение.

## 12. Ручные входы и удержание

**Типы входов** — см. §3.4. Ручной `Switch`: пока хотя бы один такой выключатель в `On`,
авто-выключение, предельный таймер и минимальное время не действуют; перевод в `Off` гасит
вытяжку сразу, если ни один другой ручной `Switch` не в `On`.

**Кнопка при поднятом ручном `Switch`.** Ручной `Switch` в `On` запрещает только
**автоматические** пути выключения (§10, §13.1). Нажатие кнопки, импульс и контакт гасят
вытяжку и при выключателе в `On`; состояние вытяжки при этом расходится с его положением
и остаётся таким, пока выключатель не даст новое событие (`On` → включить, `Off` → выключить).

**`gateBlocksManualInputs`** — действует только при выбранном `gateAutoSwitch`. Пока автоматика
запрещена, события всех трёх слотов игнорируются полностью: вытяжка по ним не включается и
не выключается. Прямое изменение самого привязанного сервиса продолжает работать. События,
пришедшие во время запрета, задним числом не применяются.

**`noAutoOffWhenManualOn`** («не отключать автоматически после ручного включения») — при
включении вытяжки кнопкой, импульсом, контактом или извне поднимается ручное удержание:
обычный таймер выключения не гасит вытяжку, остаётся только предельный таймер. Удержание
снимается при любом выключении вытяжки. Ручной вход типа `Switch` удержание не поднимает —
у него свой механизм.

**`noAutoOnAfterManualOff`** («не включать автоматически, если выключили вручную») — если
вытяжку выключили вручную или извне, пока ещё есть повод работать, ставится блокировка
авто-включения. Снимается, когда вытяжка погасла бы сама: все датчики неактивны, прошла
`offDelaySeconds` **и** условие по влажности выполнено. Возврат активности до истечения
таймаута сбрасывает отсчёт. Блокировка также снимается при любом включении вытяжки.
К ручному входу типа `Switch` не относится.

**Антидребезг** (`ignoreManualWithin5sAfterSensorOn`, по умолчанию ВКЛ) — в течение
**5 секунд** после авто-включения события кнопки, импульса и контакта игнорируются
полностью. Ручной `Switch` продолжает работать. Окно фиксировано и не настраивается.
Открывает окно **только авто-включение**, закрывает — истечение 5 секунд либо выключение
вытяжки. Событие, состояние вытяжки не меняющее (например, ручной `Switch` → `On`, когда
вытяжка уже включена), окно не перезапускает: отсчёт по-прежнему идёт от авто-включения.

## 13. Приоритеты правил при конфликтах

1. Ручной `Switch` в `On` — высший приоритет «оставаться включённой»: ни обычное
   авто-выключение, ни предельный таймер, ни минимальное время не гасят вытяжку.
2. Предельный таймер выше влажности, присутствия и минимального времени (но ниже п. 1).
3. Блокировки (`noAutoOnAfterManualOff`, блокировка после предела), пауза и запрет
   автоматики ограничивают **только** авто-включение; они не гасят уже работающую вытяжку
   и не мешают ручному/внешнему включению. Исключение — `gateBlocksManualInputs`.
4. Событие, подавленное антидребезгом или `gateBlocksManualInputs`, не порождает вообще
   никаких эффектов: ни переключения, ни установки/снятия блокировок, ни удержания.
5. Ручное удержание не действует на ручной `Switch` (§12).
6. Запрет режима «Не включать при присутствии» (§20) при активном присутствии выше любых
   поводов авто-включения — и присутствия, и влажности — и гасит работающую вытяжку
   независимо от источника включения; выше него только действующее ручное удержание
   (ручной `Switch` в `On`, п. 1, либо `manualHold` при `noAutoOffWhenManualOn`)
   и запрет автоматики «рубильником», при котором режим не действует вовсе.
7. Возврат присутствия во время продувки (§20) выше `minRunMinutes`; но `minRunMinutes`,
   больший `airingMinutes`, продувку продлевает, а предельный таймер (п. 2) остаётся выше
   и продувки, и минимального времени.

## 14. Перезапуск хаба и сохранение сценария (`onStart`)

При старте подписки создаются заново, а далее:

- вытяжка включена → момент включения считается «сейчас», предельный таймер заводится заново
  от момента старта (реальное время включения хабу неизвестно); если активности нет —
  заводится таймер выключения;
- вытяжка выключена и активность есть → начинается накопление присутствия (§6).

Перезапуск сам по себе не считается ни ручным включением, ни ручным выключением: удержание
(`noAutoOffWhenManualOn`) при старте с включённой вытяжкой не поднимается, блокировка
(`noAutoOnAfterManualOff`) при старте с выключенной не ставится. Повторный вызов `trigger`
(пересохранение сценария) не переключает вытяжку задним числом и не заставляет уже
заведённый таймер сработать дважды.

Защита от «зависших» подписок при пересохранении (поколения подписок) — деталь реализации,
наблюдаемая только косвенно; тестами не проверяется.

## 16. Краевые случаи

- **Ни один слот `motion1..3` не заполнен**: активности не бывает никогда; авто-включение
  возможно только по влажности (`humidityStartsFan`), выключение — по таймеру, заведённому
  в момент включения.
- **Датчик влажности не выбран**: условие по влажности всегда выполнено — работает чистая
  логика по присутствию.
- **Мёртвый датчик влажности** (несуществующий UUID / значение не число): условие считается
  выполненным, работает таймер присутствия, в отладочный лог пишется сообщение.
- **Контрольный датчик ниже целевой**: рабочий порог = `targetHumidity`.
- **Комната уже сухая**: условие по влажности выполнено сразу — мешать логике присутствия
  не должно.
- **`maxRunMinutes: 0`**: предела нет, вытяжка может работать сколь угодно долго.
- **`minRunMinutes: 0`, `cooldownMinutes: 0`**: соответствующие проверки отключены.
- **`onDelaySeconds: 0`**: включение при первой активности.
- **Несколько ручных `Switch`**: вытяжка гаснет только с выключением последнего.
- **Слот ссылается на несуществующий сервис**: слот считается неактивным, без ошибки сценария.
- **Один и тот же датчик в двух слотах**: повторный учёт не меняет результата.

## 20. Режим «Не включать при присутствии» (`noRunWhilePresent`, `airingMinutes`)

Раздел добавлен брифом 2026-09-23 (`spec.md` §11, четырнадцать пунктов). По смыслу
продолжает §8/§10.

Инверсия логики присутствия: пока человек в помещении — вытяжка молчит; вышел — включается
на время продувки; вернулся во время продувки — гаснет сразу. Целевой случай из брифа —
санузел.

Две опции: `noRunWhilePresent` (Boolean, `false`) и `airingMinutes` (Integer 0…1440, `5`).
**По умолчанию режим выключен, и тогда ни одно утверждение §6…§16 не меняется**, а
`airingMinutes` инертна — это отдельное утверждение, а не следствие.

При `noRunWhilePresent: true`:

1. **Пока активность датчиков есть — вытяжка выключена.** Авто-включение не выполняется,
   а работающая гаснет сразу — **независимо от того, что её включило**: продувка, работа
   по влажности, кнопка, импульс, контакт, приложение или сцена. Исключение одно —
   действующее ручное удержание: ручной вход типа `Switch` в `On` (вытяжка повторяет его
   положение, §12) либо поднятый `manualHold` при включённой `noAutoOffWhenManualOn`.
   Оба — явные пользовательские механизмы «держать включённой», и режим их не отменяет.
1a. **Правило исполняется по событиям датчиков и на старте хаба (§14) — не по факту
    включения.** Если присутствие уже активно и человек включает вытяжку сам — кнопкой,
    импульсом, контактом, из приложения или сценой, — она **остаётся работать**: нажал при
    себе, значит хотел. Асимметрия с п. 9 намеренная: там присутствие *приходит* к работающей
    вытяжке, здесь работа *приходит* к присутствию. Первый порядок в брифе назван прямо («если
    опять зашёл и работала - выключаем»), второй не назван, и п. 13 «запрет — на автоматику,
    а не на человека» решает его в пользу человека. Пара порядков проверяется рядом стоящими
    утверждениями, иначе любое из двух фиксировало бы просто исходное состояние вытяжки.
2. **Запрет сильнее влажности.** `humidityStartsFan` при активном присутствии не срабатывает,
   даже если влажность высокая (§7). Когда присутствия нет, влажность включает вытяжку
   как обычно: запрет привязан к присутствию, а не к режиму.
3. **Уход, подтверждённый `offDelaySeconds`, включает продувку.** Смысл «Задержки выключения»
   тот же, что в §6/§10, — подтвердить, что человек ушёл, а не что моргнул PIR.
4. **Продувка длится ровно `airingMinutes`, затем вытяжка выключается.** `offDelaySeconds`
   продувку не обрезает: при `offDelaySeconds` < `airingMinutes` работа идёт до конца продувки.
   Влажность продувку не заканчивает и не продлевает — условие §7 на это выключение не влияет.
5. **Визит засчитывается, только если присутствие набрало `onDelaySeconds`.** Заглянул на
   десять секунд — продувки нет. Опция сохраняет прежний смысл; меняется то, что она
   открывает: не включение при человеке, а право на продувку после него.
6. **Возврат присутствия во время продувки выключает вытяжку сразу** — сильнее `minRunMinutes`.
   Пока человек внутри, продувка не возобновляется.
7. `airingMinutes` = 0 → продувки нет: режим сводится к «никогда не включаться по присутствию».
8. `maxRunMinutes` остаётся верхним пределом и здесь: предел, наступивший раньше конца
   продувки, гасит вытяжку (§10).
9. **`minRunMinutes` больше `airingMinutes` продувку продлевает**: минимальное время работы —
   нижняя граница любого сеанса, и продувка не исключение. Сеанс идёт до `minRunMinutes`.
10. **Продувка сильнее повода по влажности в момент включения.** Если есть и право на продувку,
    и высокая влажность при `humidityStartsFan`, сеанс ведётся как продувка: фиксированные
    `airingMinutes`, влажность его не продлевает. Работа по влажности может начаться заново
    следующим событием датчика или по истечении паузы — «может», поэтому утверждением
    это не оформляется.
11. **Окончание продувки по времени — это авто-выключение**, поэтому запускает `cooldownMinutes`
    как любое другое: следующая продувка паузу ждёт. Дёрганье на границе гасится ею же.
12. **Пока `Разрешение автоматики` запрещает автоматику (§11), режим не делает ничего**:
    ни продувки после ухода, ни выключения при возврате человека. Симметрия с §11: запрет
    действует на новые попытки авто-включения и не гасит уже работающую вытяжку.
13. **Ручные входы работают как обычно** (§12): запрет — на автоматику, а не на человека.
    Ручной вход включает вытяжку и при человеке в комнате.
14. **Продувка одна на визит: закончившись, сама себя не перезапускает** — нужен новый
    засчитанный визит (присутствие, набравшее `onDelaySeconds`, и подтверждённый уход).
    Периодическая вентиляция §21 — единственный механизм, который включает вытяжку без
    нового визита, и у неё свой отсчёт.
15. **Старт хаба (§14) с включённой вытяжкой и активным присутствием гасит вытяжку**
    и начинает сессию присутствия: источник включения после перезапуска неизвестен, а
    смысл режима перевешивает. Визит отсчитывается от момента старта.
16. **Если по окончании продувки выключить не дали, потому что вернулась активность**, сеанс
    перестаёт считаться продувкой и уходит под обычный таймер выключения (§10) — то же правило,
    что §21.10 для периодической вентиляции. Один механизм, два повода: у обеих ветвей окончание
    по времени не «сгорает», а передаёт сеанс общему пути выключения. Помеха здесь одна —
    вернувшаяся активность при подвешенном режиме (п. 12): пока рубильник запрещает автоматику,
    присутствие вытяжку не гасит, поэтому окончание продувки застаёт активность и выключить
    не может. Ручное удержание помехой не считается — см. ревизию §21.10.

**Следствие.** Если вместе с режимом включён `humidityStartsFan`, после ухода человека
вытяжка может продолжить или снова начать работу по влажности: отсчёт влажности независим
от продувки, дёрганье на границе гасится `cooldownMinutes`.

**Границы, которые проверяются точно** (§19): при `airingMinutes: 5` вытяжка включена на
299-й секунде продувки и выключена на 300-й; при `offDelaySeconds: 60` уход не подтверждён
на 59-й секунде и подтверждён на 60-й; визит длительностью ровно `onDelaySeconds` засчитан;
при `minRunMinutes: 10` против продувки 5 мин вытяжка включена на 599-й секунде сеанса
и выключена на 600-й; при `maxRunMinutes: 10` против продувки 60 мин — те же 599/600.
Нижняя граница визита проверяется визитом, заведомо коротким **с учётом допуска** (10 с при
`onDelaySeconds: 120` и `offDelaySeconds: 30`): визит на секунду короче накопления попадает
в открытый вопрос §17.1 и падающим тестом не оформляется.

**Проверка «пауза после продувки» устроена парой** (иначе утверждение «продувки нет»
проходило бы и при полностью неработающем режиме): одни и те же шаги — визит, продувка,
второй визит — при `cooldownMinutes: 10` продувки не дают, при `cooldownMinutes: 0` дают.
Так же устроена и проверка рубильника: шаги те же, что в утверждениях п. 1 и п. 3,
отличается только состояние `gateAutoSwitch`.

**Не специфицировано** (ср. §18): засчитывается ли визит, набранный при запрещённой
автоматике, и что делает переход рубильника в «разрешено» после уже подтверждённого ухода;
начинается ли отложенная продувка сама по истечении `cooldownMinutes`.

## 21. Периодическая вентиляция (`airingIntervalHours`, `airingMinutes`)

Раздел добавлен вторым дополнением брифа 2026-09-23 (`spec.md` §12: одиннадцать правил плюс
уточнения 10a, 10a2 и 10b, внесённые ревизиями). По смыслу продолжает §8/§10 и §20.

Смысл: если вытяжка давно не работала и в помещении никого нет, сценарий сам проветривает —
раз в `airingIntervalHours` включает её на `airingMinutes` и выключает. Дословно по брифу:
«если нет присутствия, то раз в указанное количество времени вентиляция включается … но только
если до этого она не включалась по присутствию или вручную».

Опции: `airingIntervalHours` (Integer 0…168, `0` = выключено; рекомендация пользователя — 6,
она живёт в `desc` и дефолтом не является) и **общая** с §20 `airingMinutes` (Integer 0…1440,
`5`) — одно понятие «сколько проветривать» на два повода: продувка после ухода (§20) и
периодическая вентиляция. Отдельной опции длительности у механизма нет.

1. **Отсчёт идёт от момента, когда вытяжка последний раз выключилась.** Это и есть «только если
   до этого она не включалась»: любая работа — по присутствию (§8), по влажности (§7), ручная
   (§12), внешняя, продувка §20 — обнуляет отсчёт, и следующая периодическая вентиляция
   случится через `airingIntervalHours` **после её окончания**, а не после предыдущей.
2. **Срабатывает только при отсутствии присутствия** (§6). Если в момент истечения интервала
   активен хотя бы один заполненный слот `motion1..3` — вентиляции нет.
3. **Включение на `airingMinutes`, затем выключение** — ровно как продувка §20.4:
   `offDelaySeconds` вентиляцию не обрезает, при `offDelaySeconds` < `airingMinutes` работа
   идёт до конца вентиляции.
4. **Это авто-включение**, поэтому подчиняется тем же рамкам, что любое другое: `Разрешение
   автоматики` (§11), пауза `cooldownMinutes` (§10), предел `maxRunMinutes` (§10) и нижняя
   граница `minRunMinutes` (§10).
5. **Вместе с режимом §20**: присутствие, появившееся во время периодической вентиляции,
   гасит вытяжку сразу — по §20.1, отдельного правила не нужно.
6. **Перезапуск хаба и пересохранение сценария обнуляют отсчёт** (§14, `variables` не
   переживают старт): первая периодическая вентиляция случится через `airingIntervalHours`
   после старта.
7. `airingIntervalHours` = 0 → механизм выключен целиком: вытяжка не включается никогда,
   сколько бы времени ни прошло.
8. **Влажность вентиляцию не продлевает и не обрывает** — как продувку в §20.4. Условие §7
   на это выключение не влияет: высокая влажность держать вытяжку дольше `airingMinutes`
   не заставляет.
9. **Активность в момент истечения интервала — случай пропускается**, и отсчёт идёт заново
   на полный интервал от этого момента. Вентиляция не «ждёт в очереди» спада активности:
   комната и так проветривается работой по присутствию, а очередь означала бы включение
   сразу после ухода человека.
10. **Если по окончании проветривания выключить не дали, потому что вернулась активность**, —
    сеанс перестаёт считаться проветриванием и уходит под обычный таймер выключения (§10).
    Иначе его нечем было бы закончить, кроме предельного таймера. То же правило действует
    и для продувки §20 (см. §20.16).
    *Ревизия: сначала здесь было названо и ручное удержание. Это ошибка: под удержанием
    обычный таймер тоже бессилен (§10), поэтому сеанс законно заканчивается предельным
    таймером, и два поведения через шов неразличимы. Удержание, к тому же, поднимается только
    включением вытяжки, а во время проветривания она уже включена — внутри сеанса поднять его
    нечем. Помеха, проверяемая тестом, ровно одна: вернувшаяся активность (ср. §18).*
10a. **Продувка одна на визит и сама себя не перезапускает.** Право на неё даёт один
    подтверждённый уход после засчитанного визита; следующая продувка будет за следующий
    визит — см. §20.14.
10a2. **Принудительное выключение при присутствии паузу `cooldownMinutes` не заводит.** Пауза
    существует против дёрганья на границе порога, а здесь цикл ровно один: человек вошёл —
    выключили, вышел — проветрили. Если бы пауза заводилась, она заблокировала бы проветривание
    за тот самый визит, ради которого режим и нужен. При дефолте `0` разницы нет, при ненулевом
    видна: обычное окончание проветривания паузу заводит (§20.11), принудительное выключение
    при присутствии — нет. Этой парой правило и проверяется.
10b. **Две просьбы одновременно — остаётся последняя.** Если визит закончился в режиме §20
    и тут же истёк интервал, просьба о периодическом проветривании затирает просьбу за визит.
    Наблюдаемой разницы нет — сеанс один и той же длительности `airingMinutes`, меняется только
    текст в отладочном логе, — поэтому утверждением это не оформляется (ср. §18).
11. **Просьба о вентиляции живёт до ближайшей попытки авто-включения.** Если в момент
    истечения интервала автоматика запрещена «рубильником» (§11), вентиляция случится тогда,
    когда её разрешат — не дожидаясь следующего интервала. Так же ведёт себя и отложенная
    продувка §20.

**Границы, которые проверяются точно** (§19): при `airingIntervalHours: 1` вытяжка выключена
на 3599-й секунде ожидания и включена на 3600-й; при `airingMinutes: 5` она включена на
299-й секунде вентиляции и выключена на 300-й. Обнуление отсчёта проверяется парой границ
вокруг **двух** возможных начал отсчёта: в момент «интервал от старта» вытяжка ещё выключена,
в момент «интервал от окончания предыдущей работы» — включена. Утверждение «вытяжки нет»,
взятое в одиночку, прошло бы и при полностью неработающем механизме, поэтому проверки
рубильника и паузы устроены парами: одни и те же шаги при `gateAutoSwitch` в `Off` / в `On`
и при `cooldownMinutes` больше интервала / равном нулю.

Пункты 9 и 11 устроены **несимметрично, и это намеренно**: помеха-присутствие случай
пропускает (полный интервал заново), помеха-рубильник просьбу сохраняет (вентиляция случится,
как только разрешат). Оба утверждения проверяются точной границей, иначе их легко перепутать.

**Не специфицировано** (ср. §18): сохраняется ли просьба о вентиляции через паузу
`cooldownMinutes` так же, как через запрет рубильника (§12.4 против §12.11); засчитывается ли
«работой» включение, которое сценарий отменил в том же тике (§20.1); и достижимо ли вообще
ручное удержание внутри сеанса вентиляции — см. §18.

## 17. Открытые вопросы (падающими тестами не оформляются)

1. Что делает таймер включения, если активность пропала, а таймер сброса сессии ещё не
   сработал (провал короче `offDelaySeconds`), и в этот момент таймер включения истекает:
   спецификация трактует короткий провал как продолжение присутствия, но «включение при
   фактически отсутствующем человеке» явно не разрешено и не запрещено.
2. Перезаводится ли обычный таймер выключения после отказа выключиться (влажность выше
   порога, минимальное время не прошло): спецификация называет только события, которые
   переоценивают выключение, но не говорит о периодическом повторе.
3. Снимается ли блокировка после предельного таймера по таймеру или лениво — при следующей
   попытке включения. Наблюдаемый результат должен быть одинаков, но момент снятия не назван.
4. Что происходит со скоростью (`RotationSpeed`) в момент выключения: возвращается ли она к
   `normalSpeed` или остаётся последней записанной.
5. Точная граница окна антидребезга (ровно 5.000 с) — тестируется с запасом (3 с / 6 с).
6. Точные формулировки текста уведомления (G03) — вне контракта. Проверяются только факт
   отправки (ровно одна запись уровня `message` на один повод) и набор фактов в ней: числа
   влажности, рабочего порога и минут плюс устройство с идентификатором и комната. Порядок
   фактов, подписи к ним (в том числе ярлык рабочего порога), разбивка на строки и любая
   разметка не фиксируются.

## 18. Неспецифицированные зоны (не часть контракта)

- **Ручное удержание внутри сеанса продувки или вентиляции через шов недостижимо**, и потому
  помехой окончанию сеанса не считается (ревизия §21.10). Удержание поднимается только
  включением вытяжки кнопкой, импульсом, контактом или извне (§12), а во время продувки и
  вентиляции вытяжка уже включена — события, не меняющего её состояния, для этого не хватает
  (§19). Даже если поднять его до сеанса, при поднятом удержании ни таймер продувки, ни обычный
  таймер выключения гасить не вправе (§10): сеанс заканчивается предельным таймером и при
  исправном переводе под общий путь, и без него. Проверяется только достижимая помеха —
  «вернулась активность» (§20.16, §21.10).
- **Какая из двух одновременных просьб о проветривании выиграла** (§21.10b): длительность
  сеанса одна и та же, различает их только текст в отладочном логе, который вне контракта.

- Точный текст, формат и язык отладочных сообщений в лог; при `debug: true` проверяется
  только факт появления записей. Текст уведомления о недосушке — §17.6.
- Имена внутренних функций и полей `variables`.
- Порядок проверки независимых условий внутри конъюнкций (§8, §10).
- Поведение при значениях опций вне заявленных диапазонов (UI хаба их не допускает) и при
  дробных значениях таймеров.
- Порядок обработки нескольких одновременных событий в одном «тике».
- Взаимодействие нескольких экземпляров сценария на разных вытяжках с общими датчиками.
- Механика поколений подписок (§14) — внутренняя защита, наблюдаемого контракта не имеет.
- **Снятие таймеров прошлого поколения зелёным прогоном не доказано.** Тест §14 показывает
  лишь то, что прежний таймер выключения не гасит вытяжку после пересохранения. В стенде
  `global` и `clearTimeout` живут в одной среде, на настоящем хабе `clearTimeout`
  с идентификатором прошлого исполнения может не сработать — и защита вырождается
  в прежний колбэк-no-op: результат тот же, механизм другой. Различить их через шов нельзя.
- **Клампинг рабочего порога до 100** (`min(100, контрольный + referenceDelta)`) — ненаблюдаем:
  сама влажность ограничена 100 %, поэтому и с клампингом, и без него обе проверки §7
  («≤ порога» и «≥ порог + запас») дают один и тот же результат при любых входных данных.

## 19. Соглашения тестового стенда

- Единственный шов — DSL `ScenarioSimulator`: `scenario.info()` и
  `scenario.run({source, value, variables, options, context})` плюс виртуальные устройства.
  Одно исключение — утилита построения списков опций `collectServicesByTypes`: она общая
  с эталоном и покрыта отдельным файлом `collect-services.test.js` через
  `scenario.call('collectServicesByTypes', [types])`. Имена групп в тесте задаёт сам тест
  (функция возвращает объект с теми же ключами, что получила), поэтому имена групп
  сценария там не угадываются.
- Собственные записи сценария в привязанную характеристику **не** вызывают повторный
  `trigger` в стенде (в отличие от реального хаба). Внешнее изменение эмулируется явно:
  запись значения + повторный `scenario.run` — как в эталонном наборе.
- Время виртуальное: таймеры срабатывают только при `time.advance(...)`.
- Уведомление о недосушке (§10) доставляется через `log.message(...)`, и стенд пишет его
  отдельным уровнем `message` — `logs.byLevel('message')`. **Уровень `message` в этом сценарии
  означает именно уведомление о недосушке и ничего больше**: отладочные записи идут уровнями
  `info` и `error`. Поэтому запись отбирается в тесте по уровню, а не по словам в тексте, —
  формулировки вне контракта (§17.6), и отбор по слову уронил бы тест при верном поведении.
- Повторная запись того же значения характеристики события не порождает (кроме
  `ProgrammableSwitchEvent`, который является event-like).
- **Момент, в который подавленное событие «не ставит» блокировку `noAutoOnAfterManualOff`,
  наблюдаем только через ручной `Switch`.** Подавленное событие оставляет вытяжку
  включённой, а блокировка проявляется лишь при выключенной. Гашение таймером, пределом
  или кнопкой само меняет картину: первые два снимают блокировку по тому же условию,
  по которому снялась бы она, третье ставит свою. Исключение одно — ручной `Switch`
  в `Off`: он гасит вытяжку, блокировки не ставя (§12) и не снимая. Через него §13.4
  и проверяется — вместе с наблюдаемыми напрямую половинами: подавленное событие не
  снимает блокировку и не поднимает удержание.
