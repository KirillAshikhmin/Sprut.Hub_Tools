# Поведенческая спецификация сценария «ExternalTempSensor» (🌡️ Внешний датчик температуры для термоголовок)

Логический сценарий Sprut.Hub (один source-файл, версия на момент составления — 2.4). Назначение: привязать внешний датчик температуры к термоголовке (радиаторному термостату) — включить у неё переключатель «Внешний датчик температуры», один раз передать значение с датчика, далее держать термоголовку синхронизированной с датчиком (мгновенно по подписке, ежесуточно принудительно, и опционально — периодической «встряской», чтобы термоголовка не переключилась обратно на встроенный датчик).

Сценарий применяется индивидуально к каждой термоголовке через раздел «Логика» в её настройках (отдельный экземпляр опций/переменных на каждом устройстве).

## Глоссарий сервисов/характеристик, используемых в спецификации

| Идентификатор | Русское название | Роль в сценарии |
|---|---|---|
| `HS.Thermostat` | Термостат | Сервис термоголовки; несёт триггерящую характеристику |
| `HC.CurrentHeatingCoolingState` | Текущий режим термостата (0=Выключен, 1=Нагревает, 2=Охлаждает) | Триггерящая характеристика; также читается при «встряске» для выбора направления изменения |
| `HS.TemperatureSensor` | Датчик температуры | Тип сервиса внешнего датчика |
| `HC.CurrentTemperature` | Текущая температура | Читается с датчика (или термостата-датчика) |
| `HS.Switch` | Выключатель | Переключатель «Внешний датчик температуры» на термоголовке |
| `HC.On` | Включен (boolean) | Характеристика переключателя |
| `HS.C_TemperatureControl` | Управление температурой | Служебный сервис термоголовки, приёмник значения с внешнего датчика |
| `HC.TargetTemperature` | Целевая температура (диапазон 10–38°C, шаг 0.1°C — задан на уровне типа характеристики хаба) | Куда записывается значение с датчика и куда пишется «встряска» |
| `HS.AccessoryInformation` | Информация об аксессуаре | Несёт статус «в сети» датчика |
| `HC.C_Online` | В сети (boolean) | Онлайн-статус аксессуара датчика |

Формат идентификатора сервиса (`getUUID()`), используемый в значении опции `sensor`: строка `"<aid>.<sid>"` (id аксессуара и id сервиса через точку), например `"200.200.2"`.

## 1. Обзор и классификация

### 1.1 Тип сценария и файлы
Один файл — `source/ExternalTempSensor.js`. Содержит блок `info` и функцию `trigger`; функции `compute` нет. Отдельного глобального файла-библиотеки нет. Классификация: **логический сценарий (LOGIC)**.

### 1.2 Поддерживаемые термоголовки
Сценарий работает **только** с четырьмя моделями термоголовок, распознаваемыми по паре «модель устройства + производитель» аксессуара, на котором активирована логика:

| Публичное название | Модель (modelId) | Производитель (manufacturer) | Есть переключатель «Внешний датчик» |
|---|---|---|---|
| Aqara E1 (SRTS-A01) | `lumi.airrtc.agl001` | `Aqara` | Да |
| SONOFF TRVZB | `TRVZB` | `SONOFF` | Да |
| Danfoss 014G2463 (eTRV0101) | `eTRV0101` | `Danfoss` | Да |
| SmartKot Opentherm | `Opentherm` | `SmartKot` | **Нет** — поиск и использование переключателя полностью пропускаются |

Если аксессуар, на котором активирована логика, не соответствует ни одной из этих четырёх пар — сценарий считает термостат неподдерживаемым и полностью останавливает работу (см. §5, §11). Обхода этой проверки через опции не предусмотрено — несовместимый термостат всегда блокируется.

## 2. Триггеры запуска

### 2.1 Основная точка входа
- **Сервис-источник:** `HS.Thermostat` («Термостат») — сервис на аксессуаре термоголовки, к которой применена логика.
- **Характеристика-источник:** `HC.CurrentHeatingCoolingState` («Текущий режим термостата»).
- Сценарий вызывается хабом при **любом** изменении значения этой характеристики на данном аксессуаре — независимо от того, каким стало новое значение (0/1/2) и каким было предыдущее. Конкретное числовое значение изменения не влияет на дальнейшее поведение: при любом срабатывании выполняется одна и та же процедура настройки/синхронизации (см. §5).
- **`onStart: true`** — сценарий также запускается автоматически:
  - при старте/перезапуске хаба;
  - при каждом сохранении настроек сценария в интерфейсе (в т.ч. при активации переключателем «Активно» на термоголовке).
- Хаб различает «стартовый» запуск от обычного по параметру `context`: если его текстовое представление содержит подстроку `"HUB[OnStart]"` — запуск считается стартовым. Это влияет на серьёзность сообщений об ошибках и на то, показывается ли пользователю заметное уведомление об успешном подключении (см. §9), но НЕ влияет на состав и порядок самих проверок/действий.

### 2.2 Что игнорируется на основном входе
- Изменения любых других характеристик термоголовки (`TargetTemperature`, `TargetHeatingCoolingState`, `CurrentTemperature` самой термоголовки и т.д.) **сами по себе** не вызывают повторный запуск сценария.
- Изменения на аксессуарах, где данный экземпляр логики не активирован, полностью игнорируются.
- Простое изменение значения опции `sensor` или `changeTempPeriodically` в настройках, БЕЗ отдельного сохранения/переактивации сценария на устройстве, само по себе `trigger` не вызывает (см. также §14).

### 2.3 Вторичный (постоянный) канал обновления — подписка на датчик
После первого успешного прохождения всех проверок (см. §5) сценарий устанавливает **общесистемную** подписку: отслеживается изменение характеристики `HC.CurrentTemperature` на **любом** сервисе типа `HS.TemperatureSensor` в системе (по всем комнатам и аксессуарам, не только рядом с термоголовкой). При каждом таком событии:
- Если UUID сработавшего сервиса **точно совпадает** со значением опции `sensor` — новое значение немедленно (без задержки) записывается в `TargetTemperature` сервиса `C_TemperatureControl` термоголовки; переменные `lastTemp`/`lastUpdateTime` обновляются, если значение изменилось (см. §6, шаг 10).
- Если UUID не совпадает — событие полностью игнорируется для этого экземпляра сценария.

Эта подписка создаётся **один раз** за время жизни `variables` (т.е. до следующего перезапуска хаба) — повторные запуски `trigger` (например, при пересохранении сценария) не создают вторую подписку.

**Важная асимметрия по типу сервиса.** Опция `sensor` формально позволяет выбрать в качестве источника температуры сервис типа `HS.Thermostat` (например, встроенный датчик другой термоголовки), а не только `HS.TemperatureSensor` (см. §3.2). Однако постоянная подписка, описанная выше, отслеживает изменения только по сервисам типа `HS.TemperatureSensor`. Поэтому если пользователь выбрал в качестве датчика сервис типа «Термостат», мгновенные push-обновления по подписке для него не сработают — значение с такого «датчика» будет обновляться только в моменты принудительной синхронизации (первый запуск, ежесуточное обновление в полночь, восстановление после «встряски» — см. §2.4, §6), а не сразу при каждом изменении. Это не описано в README явно (см. «Открытые вопросы»).

### 2.4 Встроенные периодические задачи как источники эффектов
Помимо основного триггера, сценарий сам создаёт до двух периодических задач, каждая из которых может изменить характеристику `TargetTemperature` термоголовки без внешнего события:
- **Ежесуточная задача** (полночь) — создаётся всегда после первого успешного запуска, независимо от опций. Подробности — §8.
- **Задача периодической «встряски»** — создаётся, только если опция `changeTempPeriodically` > 0. Подробности — §7.

## 3. Опции конфигурации (`options`)

### 3.1 `desc`
- Тип: `String`. Значение по умолчанию: `""`.
- `formType: "status"` — чисто информационное поле в UI (текстовый статус/описание сценария), не редактируется пользователем содержательно.
- **Не влияет на поведение сценария.** Значение этой опции нигде не читается логикой — можно не учитывать при тестировании поведения.

### 3.2 `sensor` — «Датчик температуры»
- Тип: `String`. Значение по умолчанию: `""` (означает «не выбрано»).
- `formType: "list"` — выпадающий список.
- **Формирование списка:** автоматически, из ВСЕХ сервисов во всей системе (независимо от комнаты), которые являются `HS.TemperatureSensor` **или** `HS.Thermostat` и имеют характеристику `HC.CurrentTemperature`. Список отсортирован по алфавиту отображаемого имени; первый пункт всегда «Не выбрано» / `""`.
- **Список обновляется только** в момент старта хаба или сохранения сценария — устройство, добавленное в хаб позже, появится в списке только после следующего перезапуска хаба или пересохранения сценария (задокументировано в README как известное ограничение — «Логика не видит мой датчик температуры»).
- **Значение опции** — идентификатор выбранного сервиса-датчика в формате `"<aid сервиса-владельца>.<sid>"`.
- **Влияние на поведение:**
  - `""` (пусто) → сценарий выводит ошибку («Выберите внешний датчик. Если уже выбрали — активируйте сценарий заново») и полностью останавливает выполнение — ни одна из дальнейших проверок/действий не выполняется (см. §5, шаг 2).
  - Непустое значение, указывающее на существующий сервис с характеристикой `CurrentTemperature`, — используется как источник температуры для термоголовки.
  - Непустое значение, указывающее на несуществующий/удалённый аксессуар или сервис, или на «мусорную» строку без точки-разделителя, — при каждой попытке синхронизации приводит к ошибке «датчик не найден»; значение на термоголовку не передаётся (см. §6, §12). Ранее настроенные подписка и крон-задачи при этом не отключаются и продолжают попытки при следующих срабатываниях.
- **Некорректное значение** (число, битые данные, значение с более чем одной точкой) — трактуется по тому же алгоритму разбора: первый сегмент до первой точки — id аксессуара, второй сегмент — id сервиса, всё остальное игнорируется; если сервис/аксессуар с такими id не найден — ошибка «датчик не найден» (см. §12).

### 3.3 `changeTempPeriodically` — «Периодически менять значение температуры»
- Тип: `Integer`. Значение по умолчанию: `0`.
- `formType: "list"`, предлагаемые пользователю значения:
  - `0`, ключ `OFF`, «Выключено» — периодическая встряска отключена (по умолчанию).
  - `30`, ключ `MIN_30`, «30 минут (рекомендовано для Danfoss)» — встряска каждые 30 минут, порог свежести 5 минут.
  - `60`, ключ `HOUR_1`, «1 час (рекомендовано для Sonoff)» — встряска каждый час, порог свежести 60 минут.
- **Поведение:**
  - `0` (или любое значение ≤ 0) → периодическая встряска выключена: если ранее была запущена задача встряски — она останавливается и удаляется; если в этот момент «в полёте» находится отложенное 10-секундное восстановление после недавней встряски — оно тоже отменяется (см. edge-case в §12 — температура может остаться на «встряхнутом» значении до следующего реального обновления).
  - `30` → расписание встряски: каждые 30 минут по часам хаба, на 0-й и 30-й минуте (00:00, 00:30, 01:00, …). Порог свежести — 5 минут.
  - Любое другое положительное значение (включая `60`) → расписание встряски: каждый час, на 0-й минуте (00:00, 01:00, …). Порог свежести — 60 минут. Официально в UI-списке только `0/30/60`, но поведение для «не 30 и не 0» всегда сводится к часовому режиму (см. «Открытые вопросы» — не описано в README).
  - Задача встряски создаётся **один раз** — только если на момент запуска её ещё не было. Если у уже активной задачи изменить значение опции с одного положительного числа на другое положительное (например, с 30 на 60) без промежуточного выключения (0) — старое расписание и порог свежести продолжают действовать до перезапуска хаба (см. «Открытые вопросы»).

## 4. Переменные состояния (`variables`)

Значения по умолчанию (сбрасываются к этим значениям при каждом перезапуске хаба; после сброса требуется, чтобы сценарий снова успешно прошёл настройку — что обеспечивается `onStart: true`):

| Переменная | Значение по умолчанию | Наблюдаемый смысл |
|---|---|---|
| `lastTemp` | `undefined` | Последнее значение температуры, реально (с изменением) переданное на термоголовку. Не обновляется, если новое прочитанное значение равно предыдущему. |
| `lastUpdateTime` | `undefined` | Момент времени (мс) последнего РЕАЛЬНОГО изменения значения (не каждого чтения/попытки, а именно когда число изменилось). Основа для порогов свежести и суточного порога. |
| `subscribed` / `subscribe` | `false` / `undefined` | Флаг и хендл подписки на датчик (§2.3). Гарантируют, что подписка создаётся один раз за время жизни переменных. |
| `tempChangeTask` | `undefined` | Хендл активной задачи периодической встряски (§7). Существует, только пока `changeTempPeriodically` > 0 (с учётом ограничения выше о том, что расписание не пересоздаётся при смене одного положительного значения на другое). |
| `tempChangeTimeoutId` | `undefined` | Хендл отложенного (10 сек) восстановления значения после встряски. Если очередная встряска происходит раньше, чем истекли предыдущие 10 секунд, — предыдущее отложенное восстановление отменяется и запускается заново (гарантированно происходит один раз, через 10 секунд после ПОСЛЕДНЕЙ по времени встряски). |
| `midnightTask` | `undefined` | Хендл ежедневной задачи полуночного обновления (§8). Создаётся один раз, работает независимо от `changeTempPeriodically`. |

Наблюдаемое следствие «создаётся один раз»: повторные запуски `trigger` (повторные сохранения сценария, повторные срабатывания характеристики) НЕ создают вторую подписку и вторую ежесуточную/периодическую задачу. При этом переключатель «Внешний датчик» (если он нужен для типа термостата) принудительно включается заново и значение с датчика синхронизируется заново **при каждом** успешном запуске `trigger` — эти два действия не защищены от повторов.

## 5. Порядок проверок при выполнении `trigger` и приоритеты при конфликте

При каждом запуске `trigger` (по основному триггеру из §2.1) проверки и действия выполняются строго по следующему порядку; выполнение останавливается на первой обнаруженной проблеме — сообщения о последующих проблемах не появляются, пока не будет устранена текущая:

1. **Определение поддерживаемого типа термостата** по паре модель+производитель аксессуара (см. таблицу §1.2). Если пара не совпадает ни с одной из четырёх — ошибка «Поддерживаются только термостаты [список из 4 названий]. Текущий: [производитель] [модель]», выполнение полностью останавливается — ни одна другая проверка (в т.ч. выбран ли датчик) не выполняется, никакие характеристики устройства не меняются. **Наивысший приоритет.**
2. **Проверка, что опция `sensor` не пуста.** Если пуста — ошибка «Выберите внешний датчик. Если уже выбрали — активируйте сценарий заново», остановка. До этой проверки код не доходит, если термостат не распознан (шаг 1).
3. **Поиск нужных сервисов** на аксессуаре термоголовки (перебираются все сервисы аксессуара; если сервисов одного типа несколько — используется первый по порядку перечисления, остальные однотипные сервисы игнорируются):
   - `HS.Switch` / `HC.On` — только если для данного типа термостата предусмотрен переключатель (все, кроме SmartKot — см. §1.2);
   - `HS.C_TemperatureControl` / `HC.TargetTemperature` — всегда;
   - `HS.Thermostat` / `HC.CurrentHeatingCoolingState` — всегда (нужен для §7).
4. Если переключатель нужен, но не найден — ошибка «Не обнаружен переключатель [Внешний датчик температуры]», остановка.
5. Если сервис «Управление температурой» не найден — ошибка о том, что не найден сервис для передачи температуры с внешнего датчика, остановка. (Точный текст сообщения не задокументирован в README дословно — README описывает только ошибку по переключателю; см. «Открытые вопросы».)
6. Если переключатель нужен и найден — включается (`On = true`) **безусловно** при каждом успешном прохождении шагов 1–5, даже если он уже был включён ранее.
7. Выполняется однократная синхронизация значения с датчика (процедура §6).
8. Настраивается (если ещё не настроена) постоянная подписка на датчик и ежесуточная задача (§2.3, §8).
9. Настраивается или снимается периодическая встряска согласно текущему значению `changeTempPeriodically` (§7, §3.3).

**Сводные приоритеты при одновременных проблемах:**
1. Неподдерживаемый термостат — блокирует абсолютно всё, даже если датчик выбран и всё остальное корректно.
2. Отсутствие выбранного датчика — блокирует всё, что идёт после (поиск сервисов, включение переключателя, синхронизацию, подписки), но проверяется только после того, как термостат распознан.
3. Отсутствие нужных сервисов на термоголовке (сначала переключатель, затем «Управление температурой») — блокирует включение переключателя и синхронизацию, но проверяется только после успешных проверок 1–2.
4. Проблемы с самим внешним датчиком (не найден аксессуар/сервис/характеристика, невалидное значение, устаревшие данные) — проверяются последними, уже после того как переключатель термоголовки включён (шаг 6 успел выполниться независимо от исхода получения температуры).
5. Внутри проверки датчика: офлайн-статус — это предупреждение, НЕ блокирующее передачу значения; невалидное значение (null/undefined/NaN) — блокирующая ошибка, значение не передаётся. То есть строгость проверки самого значения выше, чем строгость проверки доступности устройства.
6. Ежесуточное обновление и периодическая встряска не конкурируют друг с другом и работают независимо: ежесуточное обновление происходит всегда (после первого успешного запуска), встряска — только если включена опцией.

## 6. Процедура синхронизации значения с датчика

Единая процедура, выполняемая: (а) сразу при первом успешном запуске `trigger` (шаг 7 из §5), (б) каждую полночь (§8), (в) через 10 секунд после каждой «встряски» для восстановления реального значения (§7). Шаги:

1. Разбор идентификатора `options.sensor` на id аксессуара (часть строки до первой точки) и id сервиса (часть строки между первой и второй точкой, если есть).
2. Поиск аксессуара по id. Если не найден — ошибка «внешний датчик не найден» (с указанием выбранного идентификатора), процедура прерывается для этой попытки: значение на термоголовку НЕ пишется и НЕ откатывается — остаётся прежним. Ранее настроенные подписка/крон-задачи не затрагиваются.
3. Поиск сервиса по id внутри найденного аксессуара. Если не найден — та же ошибка, тот же результат.
4. Проверка статуса «в сети» датчика: ищется сервис `HS.AccessoryInformation` на аксессуаре датчика.
   - Если такого сервиса нет вовсе — проверка полностью пропускается без каких-либо сообщений.
   - Если сервис есть, но характеристика `C_Online` отсутствует или её значение не строго равно `true` (в т.ч. `false`, `undefined`, `null`) — в лог пишется **предупреждение** «датчик не в сети», но чтение и передача значения **продолжаются** (это не блокирующая проверка).
5. Поиск характеристики `HC.CurrentTemperature` на сервисе датчика. Если отсутствует — ошибка, значение не передаётся, процедура прерывается.
6. Чтение значения температуры.
7. Валидация значения: если оно `null`, `undefined` или не является числом (`NaN`) — ошибка «невалидное значение температуры», значение **не** передаётся на термоголовку, термоголовка сохраняет предыдущее значение.
8. Проверка «разумных пределов»: если значение строго меньше −50°C или строго больше 100°C — в лог пишется **предупреждение** «подозрительное значение температуры», но значение **всё равно** передаётся на термоголовку (не блокирует). Значения ровно −50 или ровно 100 предупреждения не вызывают.
9. Значение записывается в `TargetTemperature` сервиса `C_TemperatureControl` термоголовки. (Этот сервис имеет собственный допустимый диапазон 10–38°C с шагом 0.1°C на уровне типа характеристики хаба — значение датчика вне этого диапазона, но внутри «разумных» −50…100°C, сценарий не корректирует и не блокирует; как хаб обработает запись за пределами 10–38°C — вне зоны ответственности сценария.)
10. Если только что записанное значение **отличается** от предыдущего `lastTemp` — `lastTemp` обновляется на новое значение, `lastUpdateTime` — на текущее время. Если значение **совпадает** с предыдущим `lastTemp` — ни `lastTemp`, ни `lastUpdateTime` не обновляются: метка времени «застывает» на моменте последнего реального изменения, а не последнего успешного чтения. Практическое следствие: если датчик долго и активно шлёт одно и то же (не меняющееся) значение, оно продолжает исправно записываться на термоголовку, но с точки зрения «порогов свежести» (§7, ниже) это воспринимается так, будто обновлений давно не было.
11. После этого дополнительно проверяется: если `lastUpdateTime` (уже с учётом обновления на шаге 10) старше 24 часов — фиксируется отдельная ошибка «нет показаний от датчика в течение суток или более», даже если на шаге 9 значение только что было успешно записано. Такое возможно только когда прочитанное значение равно предыдущему (шаг 10 не обновил `lastUpdateTime`) и «старая» метка времени уже старше суток.

## 7. Периодическая «встряска» температуры (`changeTempPeriodically` > 0)

Назначение (по README): термоголовки Aqara/SONOFF/Danfoss через некоторое время без активности внешнего датчика сами переключаются на встроенный датчик. Периодическая небольшая «встряска» значения имитирует активность внешнего датчика и предотвращает такое переключение.

На каждом срабатывании задачи (расписание — см. §3.3):
1. Если `lastUpdateTime` ещё ни разу не установлено — встряска выполняется (оценивать «свежесть» не от чего).
2. Иначе если с момента `lastUpdateTime` прошло **больше** 24 часов (86 400 000 мс) — встряска полностью пропускается, в лог пишется предупреждение об отсутствии данных от датчика более суток; термоголовка предоставлена сама себе и может переключиться на внутренний датчик — сценарий этому не препятствует.
3. Иначе если с момента `lastUpdateTime` прошло **строго меньше** порога свежести (5 минут для режима 30 минут; 60 минут для режима 1 час) — встряска пропускается (без предупреждения, информационным сообщением) — датчик и так недавно обновлялся и поддерживает термоголовку «живой».
4. Иначе (время с последнего обновления между порогом свежести включительно и сутками) — встряска выполняется:
   - читается **текущее** (на момент срабатывания) состояние `CurrentHeatingCoolingState` и текущее значение `TargetTemperature`;
   - если состояние = 1 («Нагревает») — температура **уменьшается** на 0.1°C; иначе (0 «Выключен», 2 «Охлаждает» или любое другое значение) — температура **увеличивается** на 0.1°C (направление изменения в README текстуально не уточняется, приведено по наиболее правдоподобной интерпретации — см. «Открытые вопросы»);
   - изменённое значение немедленно записывается в `TargetTemperature`;
   - через 10 секунд (10 000 мс) автоматически выполняется процедура синхронизации с реальным датчиком (§6) — то есть восстанавливается не «температура до встряски», а свежепрочитанное с датчика значение;
   - если очередная встряска происходит раньше, чем истекли предыдущие 10 секунд ожидания восстановления, — предыдущее ожидание отменяется и заменяется новым (восстановление гарантированно происходит один раз, через 10 секунд после последней по времени встряски);
   - если опцию `changeTempPeriodically` перевести в 0 в промежутке между моментом встряски и истечением 10-секундного окна — отложенное восстановление отменяется вместе с самой задачей: температура термоголовки может остаться на «встряхнутом» (сдвинутом на 0.1°C) значении до следующего реального события (обновление датчика по подписке, полночь).

## 8. Ежесуточное полуночное обновление

- Создаётся один раз при первом успешном прохождении проверок §5 (шаг 8), не зависит от опции `changeTempPeriodically` — работает даже если периодическая встряска выключена.
- Расписание: каждый день, ровно в 00:00:00 по времени хаба.
- Эффект: безусловно (без проверки порогов свежести) выполняет полную процедуру синхронизации значения с датчика (§6) и записывает результат на термоголовку.

## 9. Пользовательские сообщения и уровни логирования

- **Успешное первое подключение датчика:** при первом успешном создании подписки (§2.3) выводится сообщение вида «Подключен внешний датчик: [комната/название устройства]».
  - Если срабатывание произошло при старте хаба — сообщение выводится тихо (в лог, без всплывающего уведомления пользователю).
  - Если срабатывание произошло иначе (в первую очередь — пользователь вручную сохранил/активировал сценарий) — сообщение выводится как заметное уведомление пользователю (соответствует README: «При успешном запуске появится сообщение "Подключен внешний датчик"»).
  - Это сообщение показывается **только один раз** за время жизни переменных (до перезапуска хаба) — повторные запуски `trigger`, пока подписка уже установлена, его не повторяют.
- **Ошибки валидации/совместимости** (неподдерживаемый термостат, не выбран датчик, не найден переключатель/сервис управления температурой, ошибки поиска/чтения датчика):
  - Если срабатывание произошло при старте хаба — сообщение имеет пониженную серьёзность (предупреждение), чтобы не «шуметь» массовыми ошибками во время старта хаба, когда, например, датчик ещё не успел проинициализироваться.
  - Если срабатывание произошло не при старте хаба (пользователь сохранил/активировал сценарий вручную) — сообщение выводится как полноценная ошибка.
- **Предупреждения** (датчик не в сети, подозрительное значение температуры, встряска пропущена из-за отсутствия данных более суток) — всегда выводятся как предупреждения, независимо от того, стартовый это запуск или нет; ни одно из них не блокирует выполнение остальной логики.

## 11. Внешние зависимости

- **HTTP/облачные API:** не используются.
- **Солнце/геолокация:** не используются.
- **Системные часы хаба:** используются для всех cron-расписаний (полночь, каждые 30 минут, каждый час) и для расчёта интервалов свежести/суточного порога через текущее время.
- **Hub API (устройства):**
  - список всех аксессуаров/сервисов/характеристик хаба — для построения списка опции `sensor` (обновляется только на старте/сохранении, §3.2);
  - модель и производитель аксессуара термоголовки — для определения поддерживаемого типа (§1.2);
  - поиск сервисов и характеристик по типу на аксессуаре термоголовки и на аксессуаре датчика;
  - онлайн-статус (`C_Online`) аксессуара датчика — влияет только на уровень предупреждения, не блокирует (§6, шаг 4).
- **Сам внешний датчик** — единственная содержательная «внешняя» зависимость: его показания напрямую определяют, что будет записано на термоголовку; его недоступность/офлайн не останавливает работу сценария (только предупреждает), а отсутствие изменений значения дольше порогов свежести/суток влияет на решение о встряске и на диагностические сообщения.

## 12. Краевые случаи

- Пустой `options.sensor` → ошибка, полная остановка на шаге 2 (§5); ничего на устройстве не меняется.
- `options.sensor` указывает на удалённый/несуществующий аксессуар, сервис или на строку без разделителя `.` → при каждой попытке синхронизации — ошибка «датчик не найден», значение не обновляется; уже настроенные подписка/крон-задачи продолжают работать и пытаться при следующих срабатываниях.
- Значение с датчика вне диапазона [−50; 100] °C → предупреждение, значение всё равно применяется.
- Значение с датчика `null`/`undefined`/`NaN` → ошибка, значение НЕ применяется, термоголовка сохраняет прежнее значение.
- Датчик офлайн (`C_Online` ≠ `true`) → предупреждение, но если значение всё же удаётся прочитать — оно применяется; офлайн сам по себе не блокирует.
- На аксессуаре термоголовки несколько сервисов одного типа (например, два `Thermostat`) → используется первый найденный по порядку перечисления сервисов аксессуара, остальные однотипные сервисы игнорируются.
- Повторный запуск `trigger` при уже настроенной подписке/крон-задачах → подписка, ежесуточная и периодическая задачи не дублируются; при этом переключатель принудительно включается заново, и значение с датчика синхронизируется заново при каждом запуске.
- Значение от датчика равно предыдущему `lastTemp` → температура на термоголовке перезаписывается тем же числом, но `lastUpdateTime` не обновляется — «счётчик свежести» не сбрасывается, даже если датчик активно и часто присылает одно и то же значение (см. §6, шаг 10).
- `changeTempPeriodically` меняется с ненулевого значения на `0` между сохранениями → задача встряски и любое незавершённое (в пределах 10 секунд) восстановление отменяются; если восстановление было отменено «в полёте» — термоголовка может остаться на встряхнутом (сдвинутом на 0.1°C) значении до следующего реального обновления.
- `changeTempPeriodically` меняется с одного положительного значения на другое положительное (например, 30 → 60) без промежуточного выключения → расписание и порог, установленные при первом включении опции, продолжают действовать до перезапуска хаба, несмотря на новое значение в настройках (см. «Открытые вопросы»).
- Термостат не поддерживается (неверная модель/производитель) → ошибка и полная остановка, ничего на устройстве не меняется, ни одна другая проверка не выполняется.
- Более суток нет реального изменения значения от датчика:
  - при обычной синхронизации (первый запуск/полночь/восстановление после встряски) — фиксируется ошибка «нет показаний более суток» уже ПОСЛЕ того, как последнее прочитанное значение было применено (см. §6, шаг 11);
  - при периодической встряске — встряска полностью пропускается (§7, шаг 2).
- Сенсор выбран как сервис типа `Thermostat`, а не `TemperatureSensor` → мгновенные push-обновления по подписке не работают (см. §2.3); значение обновляется только в моменты принудительной синхронизации.

- Точный текст сообщения об ошибке при отсутствии сервиса «Управление температурой» (`C_TemperatureControl`) на термоголовке — README его не приводит дословно.
- Точный текст сообщений об ошибках, связанных с самим внешним датчиком (не найден аксессуар/сервис/характеристика, невалидное или подозрительное значение, «нет показаний более суток», датчик не в сети) — README не квотирует их дословно, гарантирован только факт и характер (ошибка/предупреждение) события, не буквальная формулировка.
- Поведение при изменении `changeTempPeriodically` с одного положительного значения на другое БЕЗ промежуточного выключения — действует ли новое значение немедленно, или только после перезапуска хаба (см. §12) — не описано ни в README, ни в контракте опций.
- Поведение при значениях `changeTempPeriodically`, не входящих в набор `{0, 30, 60}`, если они технически переданы в обход UI-списка.
- Гарантия немедленной ретаргетации живой подписки (§2.3) на новый датчик при изменении опции `sensor` и пересохранении сценария на уже работающей термоголовке — не гарантируется однозначно.
- Поведение при активации одного и того же экземпляра сценария сразу на нескольких термоголовках с одинаковым выбранным внешним датчиком.
- Поведение хаба (клиппинг/отклонение записи) при попытке записать в `TargetTemperature` (диапазон характеристики 10–38°C) значение с датчика или после встряски, выходящее за пределы этого диапазона, но проходящее собственную проверку сценария (−50…100°C) — это поведение уровня характеристики хаба, а не сценария, и явно не специфицировано.
- Поведение при удалении/появлении сервисов на термоголовке без повторного сохранения сценария и без перезапуска хаба.
