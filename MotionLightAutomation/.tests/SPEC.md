# Спецификация поведения: MotionLightAutomation

Версия спецификации: 2026-09-23. Источники: README.md + info-контракт (`source/MotionLightAutomation.js`).

## 1. Файлы сценария

| Файл | Роль | Комментарий |
|---|---|---|
| `source/MotionLightAutomation.js` | **LOGIC** | Единственный файл. Содержит блок `info` (`name`, `description`, `version: "1.2"`, `author: "@BOOMikru"`, `onStart: true`, `sourceServices`, `sourceCharacteristics`, `options`, `variables`) и функцию `trigger(source, value, variables, options, context)`. Функция `compute` не определена — сценарий не вычисляет значение характеристики, только реагирует на события. |

Глобального файла (библиотеки) в этом сценарии нет, поэтому вся спецификация — «логическая часть», разделы пронумерованы сквозно (без деления на 1.x/2.x).

## 2. Назначение и общая модель

Сценарий привязывается (через раздел «Логика» в настройках устройства в UI Sprut.Hub) ровно к **одному** сервису типа `Lightbulb` или `Switch` — это «управляемый свет» данного экземпляра сценария. Сценарий работает только с характеристикой `On` этого сервиса — на характеристики яркости/цвета (если сервис `Lightbulb`) он не влияет.

Назначение: включать управляемый свет автоматически по датчикам движения/присутствия/касания и выключать его по таймеру при отсутствии активности, при этом не мешая ручному управлению (выключатели, кнопки, импульсные счётчики, а также прямое управление самим управляемым светом — сценой, голосом, физическим выключателем на самой лампе).

### Терминология, используемая ниже

- **Датчик активности** — устройство, назначенное в слот `motion1`/`motion2`/`motion3` (датчик движения, присутствия или контактный датчик).
- **Активность датчиков (occupancy)** — обобщённое состояние: истинно, если активен хотя бы один из настроенных датчиков активности.
- **Ручной вход** — устройство, назначенное в слот `manualControl1`/`manualControl2`/`manualControl3` (выключатель, контактный датчик, кнопка или счётчик импульсов).
- **Управляемый свет / привязанный сервис** — сервис `Lightbulb`/`Switch`, к которому привязан данный экземпляр сценария.
- **Авто-включение** — включение управляемого света самим сценарием в результате активности датчика (см. §6).
- **Ручное/внешнее включение (выключение)** — любое включение/выключение управляемого света, которое НЕ является авто-включением/авто-выключением сценария: через ручной вход (кнопка, импульс, контакт, выключатель) либо напрямую на самом управляемом сервисе (физический выключатель, встроенный в саму лампу/реле; сцена; голосовая команда; переключение через приложение/UI хаба).
- **Ручное удержание** — режим (см. §9), в котором стандартный таймер выключения не действует, а действует только защитный таймер.
- **Блокировка повторного авто-включения** — состояние (см. §10), в котором авто-включение по датчикам временно не работает после ручного выключения.

## 3. Триггеры

### 3.1 Основной триггер (привязка сценария)

- `sourceServices`: `Lightbulb`, `Switch`.
- `sourceCharacteristics`: `On`.
- `onStart: true` — функция `trigger` вызывается: (а) при каждом запуске/перезапуске хаба; (б) при каждом сохранении настроек сценария (даже если реальные значения опций не изменились); (в) при каждом изменении характеристики `On` управляемого сервиса, независимо от того, что стало причиной изменения — сам сценарий, ручной вход, сцена, физический выключатель на лампе, приложение/UI хаба.
- Значение (`value`): `true`/`false` — новое состояние характеристики `On` на момент вызова.
- Игнорируется: изменения любых ДРУГИХ характеристик управляемого сервиса (например, яркости или цвета `Lightbulb`) не запускают сценарий.

### 3.2 Расширённое отслеживание событий (датчики и ручные входы)

Помимо основного триггера, сценарий следит за характеристиками устройств, указанных в его опциях (см. §4). Отслеживаются изменения:

- `MotionSensor.MotionDetected` — датчики движения из `motion1..3`.
- `OccupancySensor.OccupancyDetected` — датчики присутствия из `motion1..3`.
- `ContactSensor.ContactSensorState` — контактные датчики из `motion1..3` (роль «датчик активности») ИЛИ из `manualControl1..3` (роль «ручной вход»).
- `LightSensor.CurrentAmbientLightLevel` — датчик освещённости из `luxSensor`.
- `Switch.On` — выключатели из `gateAutoSwitch` («разрешение автоматики») ИЛИ из `manualControl1..3` (роль «ручной выключатель»).
- `StatelessProgrammableSwitch.ProgrammableSwitchEvent` — кнопки из `manualControl1..3`; реагирует только значение `0` («одиночное нажатие»); прочие значения этого события (двойное/долгое нажатие, если устройство их присылает) сценарием игнорируются.
- `C_PulseMeter.C_PulseCount` — счётчики импульсов из `manualControl1..3`; реагирует любое значение `> 0`.

Изменения характеристик устройств, НЕ указанных ни в одной опции сценария, игнорируются полностью, даже если тип устройства входит в отслеживаемый список выше (учитывается именно конкретный выбранный сервис, а не просто совпадение типа).

Эта расширенная реакция начинает работать по факту первого вызова `trigger`, что гарантированно происходит уже на старте хаба благодаря `onStart: true` — отдельно наблюдать «момент включения» этой реакции чёрным ящиком не требуется, достаточно считать её всегда активной после старта/сохранения сценария.

### 3.3 Активные значения характеристик датчиков

- `MotionDetected`: активно = `true`.
- `OccupancyDetected`: активно = значение, соответствующее «обнаружено» (стандартно `1`; `0` = не обнаружено). README прямо не называет число для присутствия — см. §16, открытый вопрос №1.
- `ContactSensorState`: активно = `1` («Открыто»); `0` («Закрыто») — не активно. Это относится и к роли «датчик активности», и к роли «ручной вход».
- `ProgrammableSwitchEvent`: обрабатывается только `0` («одиночное нажатие»).
- `C_PulseCount`: обрабатывается любое значение `> 0`.

### 3.4 Что запускает пересчёт авто-включения

Полная попытка авто-включения (проверка всех условий §6) выполняется при любом из событий:
- изменение датчика активности (движение/присутствие/контакт из `motion1..3`) в активное состояние;
- изменение датчика освещённости (`luxSensor`), ЕСЛИ в этот момент активность датчиков уже присутствует;
- изменение выключателя `gateAutoSwitch`, ЕСЛИ в этот момент активность датчиков уже присутствует.

Это прямо следует из README (раздел «Запрет авто-включения после ручного выключения»): «пока блокировка активна, авто-включение по датчикам (в т.ч. по событию датчика освещённости и разрешителя автоматики) не выполняется» — то есть события датчика освещённости и разрешителя автоматики САМИ ПО СЕБЕ способны инициировать попытку авто-включения (когда активность уже есть), а не только события самих датчиков активности.

## 4. Опции конфигурации (`options.*`)

### 4.0 Неповеденческие поля (заголовки групп, только оформление UI)

Следующие поля присутствуют в `info.options`, но НЕ влияют на поведение — это статусные подписи-разделители (`formType: "status"`) в UI настроек. Тестировать их не нужно:
`desc` («ОПИСАНИЕ»), `groupSensors` («ДАТЧИКИ АКТИВНОСТИ»), `groupManualControl` («РУЧНЫЕ ВХОДЫ»), `groupLight` («ОСВЕЩЁННОСТЬ»), `groupAutomationLimits` («ОГРАНИЧЕНИЯ АВТОМАТИКИ»), `groupManualHold` («РУЧНОЕ УДЕРЖАНИЕ»), `groupTimers` («ТАЙМЕРЫ ВЫКЛЮЧЕНИЯ»), `groupOther` («ПРОЧЕЕ»).

### 4.1 `motion1`, `motion2`, `motion3` — датчики активности

- Лейбл в UI: «Датчик движения или присутствия 1/2/3» (в README упрощённо называются «Датчик 1…3»).
- Тип: String, `formType: "list"`. Значение по умолчанию: `""` (не выбрано).
- Допустимые значения: `""` либо UUID сервиса типа `MotionSensor`, `OccupancySensor` или `ContactSensor`, присутствующего на хабе (список формируется динамически).
- Влияние: до 3 независимых слотов; «активность датчиков» истинна, если активен (см. §3.3) хотя бы ОДИН из настроенных (непустых) слотов. Слоты полностью равноправны и независимы (нет приоритета между `motion1`/`motion2`/`motion3`).
- Пустое значение: слот не участвует в вычислении активности.
- Некорректное значение (несуществующий сервис или сервис не того типа) — см. §14 и §16.

### 4.2 `manualControl1`, `manualControl2`, `manualControl3` — ручные входы

- Лейбл в UI: «Выключатель 1/2/3» (в README раздел называется «Ручной вход 1…3» — лейбл в UI не соответствует полному набору принимаемых типов устройств, см. §16, открытый вопрос).
- Тип: String, `formType: "list"`. Значение по умолчанию: `""` (не выбрано).
- Допустимые значения: `""` либо UUID сервиса одного из типов: `Switch`, `ContactSensor`, `StatelessProgrammableSwitch` (кнопка), `C_PulseMeter` (счётчик импульсов).
- Влияние (по типу назначенного сервиса, см. подробно §7–§11):
  - `Switch` — управляемый свет «следует» за состоянием этого выключателя (не toggle): включается при переходе в `On`, выключается при переходе в `Off`, если при этом ни один ДРУГОЙ настроенный ручной `Switch` не в `On`.
  - `ContactSensor` — работает только на включение (НЕ toggle): «Открытие» (переход `ContactSensorState` → `1`) включает свет, если он выключен; если свет уже включён — свет НЕ выключается, а таймер выключения перезапускается: обычный `offDelaySeconds` (либо защитный `manualHoldSafetyOffDelayMinutes`, если действует удержание §9) начинает отсчёт заново с момента этого «Открытия». Режим удержания при этом не меняется (не активируется и не снимается). Если в момент «Открытия» есть активность датчиков или ручной `Switch` в `On` — таймер не запускается (в этих состояниях он и так не идёт, см. §7/§8). «Закрытие» (→ `0`) игнорируется полностью, удержания состояния нет.
  - `StatelessProgrammableSwitch` (кнопка) — одиночное нажатие (`ProgrammableSwitchEvent = 0`) переключает свет (toggle).
  - `C_PulseMeter` (счётчик импульсов) — любое значение `C_PulseCount > 0` переключает свет (toggle).
- До 3 независимых слотов, можно комбинировать разные типы одновременно (например, `manualControl1` = выключатель, `manualControl2` = кнопка).
- Пустое значение: слот не используется.
- Важно (из README «Важные замечания»): не следует назначать сюда сам управляемый свет, если он `Switch` (устройство, к которому привязан этот экземпляр сценария) — это создаёт конфликт логики.

### 4.3 `luxSensor` — датчик освещённости

- Тип: String, `formType: "list"`. Значение по умолчанию: `""` (не выбрано).
- Допустимые значения: `""` либо UUID сервиса `LightSensor`.
- Влияние: необязательный параметр. Если задан — авто-включение по датчикам блокируется, когда `CurrentAmbientLightLevel` этого датчика ВЫШЕ `maxAmbientLux` (см. §4.4). Если пусто — ограничения по освещённости нет (авто-включение всегда разрешено с этой стороны). Ручное/внешнее включение НИКОГДА не ограничивается освещённостью.
- Некорректное значение — см. §14/§16.

### 4.4 `maxAmbientLux` — порог освещённости (люкс)

- Тип: Integer. Значение по умолчанию: `50`. Диапазон: `0`…`100000`, шаг `1`.
- Влияние: используется только если задан `luxSensor`. Авто-включение разрешено, если текущая освещённость `≤ maxAmbientLux` (включая равенство — «не выше» из README); заблокировано, если строго `> maxAmbientLux`. Если `luxSensor` пуст, значение этой опции не используется, каким бы оно ни было.
- Некорректное значение (вне диапазона, дробное, отрицательное) — не описано; см. §16.

### 4.5 `gateAutoSwitch` — разрешение автоматики

- Тип: String, `formType: "list"`. Значение по умолчанию: `""` (не выбрано).
- Допустимые значения: `""` либо UUID сервиса `Switch`.
- Влияние: необязательный «шлюз». Пока этот выключатель в `On` — авто-включение по датчикам разрешено; пока в `Off` — авто-включение по датчикам заблокировано (доступно только ручное/внешнее включение). Если пусто — ограничения нет, авто-включение всегда разрешено с этой стороны. Ручное/внешнее включение по умолчанию НЕ ограничивается этим выключателем; исключение — включённая опция `gateBlocksManualInputs` (§4.6.1), которая распространяет запрет и на ручные входы.
- Переключение `gateAutoSwitch` в состояние «запрещено» НЕ выключает уже горящий свет немедленно — оно только блокирует НОВЫЕ попытки авто-включения; уже включённый свет продолжает подчиняться обычным правилам выключения (§7–§9).
- Важно (README «Важные замечания» п.3): нельзя назначать один и тот же `Switch` одновременно в `gateAutoSwitch` и в `manualControl1..3` — см. приоритет в §12.

### 4.6 `gateAutoSwitchInvert` — инвертировать «Разрешение автоматики»

- Тип: Boolean. Значение по умолчанию: `false`.
- Влияние: используется только вместе с непустым `gateAutoSwitch`. При `true` логика инвертируется: авто-включение разрешено, пока `gateAutoSwitch` в `Off`, и заблокировано, пока в `On`. При `false` — обычная логика (разрешено, пока `On`).
- Если `gateAutoSwitch` пуст — значение этой опции не влияет ни на что.
- Некорректное (не boolean) значение — не описано; см. §16.

### 4.6.1 `gateBlocksManualInputs` — «Также не реагировать на ручные входы»

- Тип: Boolean. Значение по умолчанию: `false`.
- Влияние: используется только вместе с непустым `gateAutoSwitch`. При `true` и в момент, когда `gateAutoSwitch` (с учётом `gateAutoSwitchInvert`) запрещает автоматику, события ВСЕХ ручных входов `manualControl1..3` игнорируются полностью: ручной `Switch` (и `On`, и `Off`), кнопка, счётчик импульсов, контактный датчик в роли ручного входа. Свет по ним не включается И не выключается, удержание не активируется и не снимается, блокировка `noAutoOnAfterManualOff` не ставится и не снимается.
- При `false` (по умолчанию) ручные входы работают всегда, независимо от `gateAutoSwitch`.
- Если `gateAutoSwitch` пуст — значение этой опции не влияет ни на что (блокировки нет).
- Запрет не распространяется на изменение состояния самого управляемого света (сцена, голос, физический выключатель, напрямую управляющий лампой) — такие события сценарий обрабатывает всегда (§3.1).
- Игнорирование не «отложенное»: события, пришедшие во время запрета, не применяются задним числом после того, как `gateAutoSwitch` снова разрешит автоматику. Свет не подстраивается под текущее положение ручного `Switch` до следующего его события.
- Уже горящий свет опция сама по себе не гасит и не включает.

### 4.7 `noAutoOffWhenManualOn` — «Не отключать свет автоматически после ручного включения»

- Тип: Boolean. Значение по умолчанию: `false`.
- Влияние: подробно см. §9 «Ручное удержание». Кратко: при `true` включение света кнопкой/импульсом/контактом-ручным-входом ИЛИ ручное/внешнее включение самого управляемого света (сцена, голос, физический выключатель на лампе) активирует режим удержания — вместо обычного таймера `offDelaySeconds` начинает действовать только защитный таймер `manualHoldSafetyOffDelayMinutes`. При `false` (по умолчанию) такое включение подчиняется обычному таймеру `offDelaySeconds`, как только активность датчиков отсутствует.
- На «следование» ручному `Switch` (§8) эта опция НЕ влияет — тот механизм независим.

### 4.8 `noAutoOnAfterManualOff` — «Не включать свет автоматически, если его отключили вручную»

- Тип: Boolean. Значение по умолчанию: `false`.
- Влияние: подробно см. §10 «Блокировка повторного авто-включения». Кратко: при `true` ручное/внешнее выключение света (кнопкой, импульсом, контактом-ручным-входом или напрямую сценой/голосом/физическим выключателем на лампе) в момент, когда датчики ещё активны, блокирует последующее авто-включение по датчикам до момента, когда свет погас бы сам (все датчики неактивны и прошёл таймаут `offDelaySeconds`). Не относится к ручному входу типа `Switch` (переход в `Off` там — штатное состояние автоматики, а не «ручное выключение» для целей этой опции).
- При `false` (по умолчанию) — блокировки нет, датчик может немедленно снова включить свет после любого ручного выключения.

### 4.9 `ignoreManualWithin5sAfterSensorOn` — «Игнорировать кнопку/импульс 5 секунд после включения по датчику»

- Тип: Boolean. Значение по умолчанию: **`true`** (единственная Boolean-опция, включённая по умолчанию).
- Влияние: подробно см. §11 «Антидребезг». Длительность окна фиксирована — **5 секунд (5000 мс)** — и НЕ настраивается отдельной опцией, эта опция только включает/выключает сам механизм.
- При `true` — в течение 5 секунд после авто-включения СВЕТА ПО ДАТЧИКУ события от кнопки, счётчика импульсов и контакта-ручного-входа игнорируются полностью (и попытка включить, и попытка выключить). Ручной `Switch` не подавляется никогда.
- При `false` — окна нет, ручные события обрабатываются немедленно всегда.

### 4.10 `offDelaySeconds` — задержка выключения (с)

- Тип: Integer. Значение по умолчанию: `30`. Диапазон: `0`…`86400` (24 часа), шаг `1`.
- Влияние: подробно см. §7 «Автоматическое выключение». Основная задержка перед выключением света после того, как ВСЕ датчики активности стали неактивными (при отсутствии ручного удержания и отсутствии включённого ручного `Switch`); та же величина используется как задержка выключения, когда управляемый свет включён «извне» (сценой/выключателем на лампе/т.п.) при отсутствии активности датчиков и без удержания (§7); та же величина используется как срок ожидания снятия блокировки `noAutoOnAfterManualOff` (§10).
- Значение `0` — выключение происходит немедленно (без ожидания), как только выполнены условия выключения на момент проверки.
- README рекомендует ставить не менее 30 секунд для защиты от ложных выключений — это рекомендация, а не ограничение (минимально допустимое значение по контракту — `0`).
- Некорректное значение (вне диапазона, дробное, отрицательное) — не описано; см. §16.

### 4.11 `manualHoldSafetyOffDelayMinutes` — задержка выключения после ручного включения (мин)

- Тип: Integer. Значение по умолчанию: `240` (4 часа). Диапазон: `0`…`10080` (7 суток), шаг `1`.
- Влияние: защитный таймер режима «ручное удержание» (§9) — единственный способ автоматически выключить свет, пока действует удержание. Единицы измерения — минуты.
- Значение `0` отключает защитный таймер полностью: пока действует удержание, автоматика никогда не выключит свет по времени (только ручное/внешнее выключение или потеря удержания иным путём).

### 4.12 `debug` — режим отладки

- Тип: Boolean. Значение по умолчанию: `false`.
- Влияние: включает подробные информационные сообщения в лог сценария о принимаемых решениях. НЕ влияет на логику автоматики/итоговое состояние света — исключительно диагностика. Содержимое и точный текст сообщений — вне контракта (см. §17); допустимо проверять лишь факт наличия/отсутствия записей в логе при `debug=true`/`false`, если тестовый стенд это поддерживает.

## 5. Переменные состояния (`variables`)

Все перечисленные ниже переменные — часть `info.variables`, то есть часть публичного состояния сценария между вызовами.

- `cachedLightService` (по умолчанию `undefined`) — ссылка на управляемый сервис. Наблюдаемый эффект: сценарий всегда управляет тем сервисом, к которому привязан.
- `externalSubscribed` (по умолчанию `false`) — признак того, что расширенное отслеживание событий (§3.2) уже активно. Наблюдаемый эффект: после первого вызова `trigger` (гарантированно происходит при старте/сохранении благодаря `onStart: true`) сценарий реагирует на события датчиков/ручных входов/шлюза/освещённости.
- `manualHold` (по умолчанию `false`) — признак активного режима «ручное удержание» (§9).
- `offTimerId` (по умолчанию `undefined`) — признак запланированного обычного таймера выключения (`offDelaySeconds`).
- `manualHoldSafetyTimerId` (по умолчанию `undefined`) — признак запланированного защитного таймера ручного удержания (`manualHoldSafetyOffDelayMinutes`).
- `lastSensorAutoOnAt` (по умолчанию `undefined`) — момент последнего авто-включения по датчику; используется только для окна антидребезга (§11).
- `manualOffLock` (по умолчанию `false`) — признак активной блокировки повторного авто-включения после ручного выключения (§10).
- `manualOffLockTimerId` (по умолчанию `undefined`) — признак запланированного отсчёта снятия этой блокировки.

**Сброс**: все переменные возвращаются к значениям по умолчанию при перезапуске хаба и при каждом сохранении настроек сценария (стандартная платформенная семантика — `variables` реинициализируется). Наблюдаемый эффект: любое незавершённое состояние (активное удержание, запланированные таймеры, активная блокировка) теряется при перезапуске/пересохранении сценария; дальнейшее поведение определяется заново со следующего входящего события (и с самого вызова `trigger` при старте/сохранении, см. §3.1). Что именно происходит, если на момент такого перезапуска управляемый свет уже включён, README не описывает — см. §16, открытый вопрос №2.

## 6. Автоматическое включение по датчикам

Полное условие авто-включения (все пункты обязательны, конъюнкция — порядок проверки не наблюдаем и не важен, важен только итог):

1. Активна хотя бы один из настроенных датчиков активности (`motion1..3`, см. §3.3, §4.1).
2. Разрешено автоматическое включение выключателем `gateAutoSwitch` (если он задан — с учётом `gateAutoSwitchInvert`; если не задан — условие всегда выполнено).
3. Освещённость не выше `maxAmbientLux` (если задан `luxSensor`; если не задан — условие всегда выполнено).
4. Управляемый свет в данный момент выключен.
5. Не активна блокировка повторного авто-включения `manualOffLock` (см. §10; учитывается только если включена опция `noAutoOnAfterManualOff`).

Проверка (и потенциальное включение) выполняется при событиях, перечисленных в §3.4.

## 7. Автоматическое выключение

Свет выключается по истечении `offDelaySeconds` (см. §4.10), если на момент срабатывания ОДНОВРЕМЕННО:
- все настроенные датчики активности неактивны;
- НЕ активен ни один ручной `Switch` в состоянии `On` (см. §8 — это условие имеет приоритет надо всем остальным);
- НЕ активно ручное удержание (`manualHold` = `false`, см. §9).

Отсчёт `offDelaySeconds` начинается в момент, когда ПОСЛЕДНИЙ активный датчик становится неактивным (то есть в момент перехода «активность есть» → «активности нет»). Если до истечения таймера активность появляется вновь (на любом из настроенных датчиков) — отсчёт отменяется; полноценный новый отсчёт начнётся заново только после следующей потери всей активности.

«Открытие» контакта-ручного-входа (§4.2) при уже включённом свете и отсутствии активности датчиков ПЕРЕЗАПУСКАЕТ отсчёт: свет погаснет через `offDelaySeconds` после последнего такого «Открытия», а не после исходного момента потери активности/включения. В режиме удержания (§9) так же заново запускается защитный таймер `manualHoldSafetyOffDelayMinutes`.

Значение `offDelaySeconds = 0` — свет выключается немедленно в момент потери активности (без ожидания), при условии, что остальные условия выше выполнены в этот момент.

### Включение «извне» при отсутствии активности датчиков

Если управляемый свет включился внешним действием (напрямую на самом сервисе: физический выключатель на лампе, сцена, голосовая команда, ручное переключение через приложение/UI) и в момент включения датчики неактивны:
- при `noAutoOffWhenManualOn = false` (по умолчанию) — запускается обычный таймер `offDelaySeconds`, свет погаснет через это время (если активность так и не появится);
- при `noAutoOffWhenManualOn = true` — вместо этого активируется ручное удержание (§9): обычный таймер не используется, действует только защитный таймер `manualHoldSafetyOffDelayMinutes`.

Важно: это верно даже при полностью пустой конфигурации (без единого настроенного датчика/ручного входа) — «активности» тогда никогда не бывает, поэтому ЛЮБОЕ включение света (любым способом) при `noAutoOffWhenManualOn = false` неизбежно погаснет через `offDelaySeconds` (по умолчанию — через 30 секунд).

Переключение `gateAutoSwitch` в «запрещено» или рост освещённости выше `maxAmbientLux` НЕ выключают уже горящий свет — они лишь блокируют новые попытки авто-включения (см. §4.5, §4.3).

## 8. Удержание ручным выключателем (`manualControl` типа `Switch`)

Если хотя бы один слот `manualControl1..3` — устройство типа `Switch`:

- при переходе такого выключателя в `On` — управляемый свет немедленно включается и «следует» за состоянием выключателя (не toggle — прямое повторение состояния);
- пока ХОТЯ БЫ ОДИН настроенный ручной `Switch` находится в `On` — ни обычный таймер `offDelaySeconds`, ни защитный таймер `manualHoldSafetyOffDelayMinutes` не могут выключить свет. Это действует НЕЗАВИСИМО от значений опций `noAutoOffWhenManualOn` и `noAutoOnAfterManualOff` — эти опции относятся только к кнопкам, импульсам и контакту-ручному-входу, а не к ручному выключателю;
- при переходе конкретного ручного `Switch` из `On` в `Off`: если ни один из ОСТАЛЬНЫХ настроенных ручных `Switch` не в `On` — свет выключается немедленно; если хотя бы один из остальных ещё в `On` — свет остаётся включённым;
- механизм не зависит от активности датчиков движения/присутствия: пока ручной `Switch` включён, свет горит вне зависимости от того, есть активность или нет;
- опция `noAutoOnAfterManualOff` НЕ применяется к этому механизму: переход ручного `Switch` в `Off` не считается «ручным выключением» для целей блокировки повторного авто-включения (§10) — это штатное автоматическое состояние.

## 9. Ручное удержание («РУЧНОЕ УДЕРЖАНИЕ»)

Применимо только когда `noAutoOffWhenManualOn = true`.

### Активация

Удержание активируется при любом из событий (проверяется заново при каждом включении света — предыдущее состояние удержания значения не имеет):
- свет включили кнопкой, счётчиком импульсов или контактом-ручным-входом, привязанным к `manualControl1..3`;
- свет включили «извне» — напрямую на самом управляемом сервисе (физический выключатель на лампе, сцена, голосовая команда, приложение/UI хаба) — см. §7.

Включение ручным `Switch` (§8) — отдельный, самостоятельный механизм, режим «ручное удержание» в этом случае не активируется (в нём не нужен, т.к. §8 сам по себе блокирует оба таймера, пока `Switch` в `On`).

### Поведение в режиме удержания

- стандартный таймер `offDelaySeconds` не выключает свет;
- как только активность датчиков пропадает (или её изначально не было) — запускается защитный таймер `manualHoldSafetyOffDelayMinutes`;
- пока есть активность хотя бы одного датчика — защитный таймер не запущен/не тикает;
- по срабатыванию защитного таймера свет выключается, ЕСЛИ на этот момент активности всё ещё нет (и ни один ручной `Switch` не в `On`); если активность к этому моменту вернулась — выключение не происходит (таймер, по наиболее логичной трактовке, начинает отсчёт заново после следующей потери активности — README явно описывает такой сброс только для `offDelaySeconds` и для окна снятия блокировки §10, не для этого таймера отдельно; см. §16, открытый вопрос №4).

### Завершение удержания

Удержание действует, пока управляемый свет остаётся непрерывно включённым после активирующего события; оно перестаёт быть актуальным, когда свет гаснет любым способом (защитным таймером, ручным/внешним выключением) — при следующем включении режим удержания вычисляется заново по правилам активации выше.

## 10. Блокировка повторного авто-включения после ручного выключения

Применимо только когда `noAutoOnAfterManualOff = true`.

- **Установка блокировки**: происходит, когда свет ВЫКЛЮЧИЛИ кнопкой, импульсом ИЛИ «извне» (сценой, голосом, физическим выключателем на лампе) В МОМЕНТ, когда хотя бы один датчик активности ещё активен. Контакт-ручной-вход свет не выключает (§4.2), поэтому блокировку поставить не может.
- **Действие блокировки**: пока блокировка активна, авто-включение по датчикам НЕ выполняется — включая попытки, инициированные событием датчика освещённости или выключателя `gateAutoSwitch` (см. §3.4). Ручное/внешнее включение (кнопкой, импульсом, контактом, ручным `Switch`, сценой и т.п.) блокировкой НЕ ограничено — работает всегда.
- **Снятие блокировки** происходит:
  - немедленно — при любом включении света (ручном или внешнем, любым способом);
  - автоматически — в момент, когда свет погас бы сам: ВСЕ датчики активности стали неактивны И с этого момента прошёл таймаут `offDelaySeconds`. Пока есть активность хотя бы на одном датчике — отсчёт этого таймаута не идёт, блокировка держится. Если активность возвращается ДО истечения таймаута — отсчёт сбрасывается и начнётся заново после следующей полной потери активности.
- **Исключение**: не относится к ручному входу типа `Switch` — переход такого выключателя в `Off` НЕ ставит блокировку (это штатное автоматическое состояние, а не «ручное выключение», см. §8).

## 11. Антидребезг кнопки/импульса/контакта после авто-включения по датчику

Применимо только когда `ignoreManualWithin5sAfterSensorOn = true`. Окно фиксировано — **5 секунд (5000 мс)**, не настраивается.

- Окно начинается в момент АВТО-включения света ПО ДАТЧИКУ (переход выключено→включено именно в результате §6), а не при любом включении светa. Ручное/внешнее включение окно не открывает.
- Пока действует окно (менее 5 секунд с момента этого авто-включения):
  - события от кнопки, счётчика импульсов и контакта-ручного-входа (`manualControl1..3`) игнорируются ПОЛНОСТЬЮ — попытки включить (а для кнопки/импульса — и выключить) свет этими устройствами не производят никакого эффекта;
  - ручной `Switch` (§8) продолжает работать без каких-либо ограничений;
  - сами датчики активности (§6/§7) и обычные/защитные таймеры выключения продолжают работать без ограничений — подавляются только события ручного входа перечисленных трёх типов.
- Окно отсчитывается по времени с момента авто-включения, а НЕ по текущему состоянию света: если свет успел погаснуть (например, по очень короткому `offDelaySeconds`) до истечения 5 секунд, попытки включить его кнопкой/импульсом/контактом в оставшееся время окна ВСЁ РАВНО игнорируются.
- Повторные срабатывания датчика активности, пока свет уже включён, окно НЕ продлевают и не переоткрывают (новое авто-включение, а значит и новое окно, возможно только из состояния «выключено», см. §6 п.4).
- По истечении 5 секунд с момента авто-включения кнопка/импульс/контакт-ручной-вход снова обрабатываются штатно (кнопка/импульс — toggle, контакт — только включение, см. §4.2).
- При `ignoreManualWithin5sAfterSensorOn = false` окна нет вовсе — ручные события обрабатываются немедленно в любой момент.

## 12. Приоритеты правил при конфликтах

1. **Ручной `Switch` в `On` — наивысший приоритет для «оставаться включённым»**: пока хотя бы один настроенный ручной `Switch` в `On`, свет не может быть выключен ни обычным, ни защитным таймером, независимо от любых других опций (§8).
2. **Один и тот же `Switch` назначен одновременно в `gateAutoSwitch` и в `manualControl1..3`** (запрещённая README конфигурация, «Важные замечания» п.3): событие обрабатывается веткой «разрешение автоматики» — ветка «ручной вход» для этого устройства не сработает.
3. **Один и тот же контактный датчик назначен одновременно в `motion1..3` и в `manualControl1..3`** (запрещённая README конфигурация, «Важные замечания» п.6): событие обрабатывается веткой «ручной вход» (включает свет на каждое «Открытие», если он выключен; горящий свет не гасит) — не как срабатывание датчика активности. Влияет ли это на то, учитывается ли ТЕКУЩЕЕ состояние этого контакта как активность датчика при ДРУГИХ событиях — README не уточняет, см. §16.
4. **Подавленное антидребезгом событие (§11) не порождает никаких других эффектов** — ни toggle, ни установку/снятие блокировки (§10), ни активацию удержания (§9): событие полностью проигнорировано на входе.
5. **`gateAutoSwitch`/`maxAmbientLux`/`manualOffLock` ограничивают ТОЛЬКО путь авто-включения по датчику** — ни один из них не ограничивает и не отменяет ручное/внешнее включение или выключение, и ни один не выключает уже горящий свет самостоятельно. Единственное исключение — `gateBlocksManualInputs = true` (§4.6.1): при запрещающем `gateAutoSwitch` ручные входы `manualControl1..3` игнорируются целиком (но и в этом случае уже горящий свет не гасится, а внешнее изменение самого света обрабатывается штатно).
6. **`noAutoOnAfterManualOff` не применяется к ручному входу типа `Switch`**, а `noAutoOffWhenManualOn` и `manualHoldSafetyOffDelayMinutes` не применяются к удержанию, вызванному ручным `Switch` (§8) — это два полностью независимых, самодостаточных механизма.

## 14. Краевые случаи

- **Пустые значения опций-списков** (`motion1..3`, `manualControl1..3`, `luxSensor`, `gateAutoSwitch` = `""`): соответствующая роль/слот не участвует в логике (как будто не настроен). При пустом `gateAutoSwitch` опции `gateAutoSwitchInvert` и `gateBlocksManualInputs` не влияют ни на что.
- **`offDelaySeconds = 0`**: выключение немедленно при потере активности (или сразу при включении «извне» без активности и без удержания).
- **`maxAmbientLux = 0`**: авто-включение возможно только при освещённости `≤ 0`.
- **`manualHoldSafetyOffDelayMinutes = 0`**: защитный таймер отключён — в режиме удержания свет никогда не выключится по времени.
- **Полностью пустая конфигурация** (ни одного датчика, ни одного ручного входа): авто-включение по датчику никогда не происходит; свет включается только ручным/внешним способом; при `noAutoOffWhenManualOn = false` (по умолчанию) любое такое включение погаснет через `offDelaySeconds` (т.к. активности «нет» всегда).
- **Ссылка опции на несуществующий/удалённый сервис**: README не описывает; предполагается, что слот трактуется как неактивный/не задействованный, без ошибки сценария (см. §16).
- **Ссылка опции на сервис не того типа, что ожидается для роли** (возможно только в обход UI, так как список выбора в UI ограничен подходящими типами): README не описывает; предполагается, что слот трактуется как неактивный, без ошибки (см. §16).
- **Оффлайн-устройство** (существует на хабе, но физически недоступно): README и info-контракт не упоминают проверку онлайн-статуса; поведение не специфицировано (см. §16) — по общей практике платформы, вероятно используется последнее известное значение характеристики.
- **Один и тот же сервис назначен дважды в однотипные слоты** (например, `motion1 = motion2`, либо `manualControl1 = manualControl2` с одним и тем же устройством): не описано явно; ожидаемо безвредно — повторный учёт того же устройства не должен менять итоговый результат.
- **Повторные одинаковые значения характеристики** (например, повторная установка того же значения `MotionDetected`/`On`): по общей платформенной практике Sprut.Hub уведомление о смене характеристики происходит только при реальном изменении значения — повторная установка ТОГО ЖЕ значения обычно не порождает новое событие. Это платформенное поведение, не специфика сценария; для характеристик-событий (`ProgrammableSwitchEvent`, `C_PulseCount`) поведение при повторении того же числового значения — вне зоны ответственности сценария (см. §16).
- **Два и более ручных `Switch` включены одновременно**, затем выключаются по одному: свет остаётся включённым, пока хотя бы один в `On`, гаснет сразу с выключением последнего (§8).
- **Присутствие на одном датчике держится, а на другом появляется/пропадает движение** (при активной блокировке §10): блокировка держится, пока есть активность хотя бы НА ОДНОМ датчике из настроенных — снятие требует одновременной неактивности ВСЕХ.

## 15. Внешние зависимости

- **HTTP/внешние API**: не используются.
- **Cron / расписания**: не используются.
- **Время суток / восход-закат**: сценарий не содержит логики «день/ночь» — при необходимости ограничения по времени суток пользователь должен подключить отдельный виртуальный выключатель ко входу `gateAutoSwitch` (см. пример 1 в README).
- **Системное время хаба**: используется для всех таймеров и окон (§13) — сценарий зависит от корректности системных часов хаба.
- **Состояния устройств хаба**: сценарий читает характеристики выбранных сервисов «по требованию» в момент проверки условий; поведение при недоступности/офлайн устройства не специфицировано (см. §16).
- **Платформенный механизм подписки/уведомлений об изменении характеристик**: сам факт и момент получения уведомления о смене характеристики — вне контроля сценария, это гарантия платформы (см. также «повторные значения» в §14).

## 16. Открытые вопросы

1. README не называет явно, какое числовое значение `OccupancyDetected` соответствует «присутствие обнаружено» (для датчика движения и контакта числа/состояния названы явно — `true` и «Открыто» соответственно). В спецификации (§3.3) принято стандартное значение `1` = обнаружено. Требует подтверждения.
2. README не описывает поведение сценария в момент запуска хаба/сохранения сценария, если управляемый свет НА ЭТОТ МОМЕНТ уже включён (например, остался включённым с прошлой сессии): активируется ли режим «ручное удержание» (если `noAutoOffWhenManualOn = true`), запускаются ли таймеры выключения, или свет просто остаётся в текущем состоянии до следующего события. Это прямое следствие сброса `variables` при перезапуске (§5), но конкретный результат README не специфицирует.
3. Снято в версии 1.2: README явно называет контакт-ручной-вход среди событий, активирующих удержание (§9), наравне с кнопкой и импульсом.
4. README явно описывает сброс отсчёта при возврате активности до истечения таймаута для `offDelaySeconds` (§7) и для окна снятия блокировки `noAutoOnAfterManualOff` (§10), но НЕ говорит явно то же самое про защитный таймер `manualHoldSafetyOffDelayMinutes` (§9) — сказано лишь, что он «запускается при отсутствии активности» и срабатывает, «если активности всё ещё нет». В спецификации принято поведение по аналогии (сброс/перезапуск отсчёта при возврате активности) как наиболее логичное и не противоречащее README, но это предположение, а не прямая цитата.
5. Поведение при ссылке опции (`motion1..3`, `manualControl1..3`, `luxSensor`, `gateAutoSwitch`) на несуществующий/удалённый сервис или на сервис не того типа, что ожидается для роли, — не описано ни в README, ни в info-контракте (там заданы только списки допустимых значений для UI). В спецификации принято наиболее безопасное для пользователя поведение — «слот считается неактивным, без ошибки», это предположение.
6. Поведение при недоступном (оффлайн) устройстве, ссылка на которое настроена в опции, — не упомянуто ни в README, ни в info-контракте.
7. Точная граница окна антидребезга (§11): формулировка README «в течение 5 секунд» не уточняет, включается ли момент ровно t=5.000с в подавляемый интервал или нет. Рекомендуется тестировать с запасом (например, 4.9с/5.1с), а не ровно на границе.
8. Лейбл опции `manualControl1` в UI — «Выключатель 1» — не отражает, что слот принимает также контакт, кнопку и счётчик импульсов; README называет этот же раздел «Ручной вход». Это расхождение именования (info-контракт vs README), не поведенческое, но может ввести в заблуждение при чтении одних лишь названий полей.
9. Точная семантика конфликта «контакт одновременно в датчиках активности и в ручных входах» (§12 п.3): README говорит, что событие уходит в ветку «ручной вход», но не уточняет, продолжает ли ТЕКУЩЕЕ состояние этого контакта учитываться как активность датчика при возникновении ДРУГИХ событий (например, срабатывании иного датчика движения) — то есть перестаёт ли контакт быть «источником активности» полностью, или только конкретное его событие обрабатывается иначе.
10. Поведение при значениях числовых опций (`maxAmbientLux`, `offDelaySeconds`, `manualHoldSafetyOffDelayMinutes`) вне заявленного диапазона `minValue`/`maxValue`, дробных или отрицательных значениях — не описано ни в README, ни в info-контракте (там заданы только ограничения для UI-редактора).

## 17. Неспецифицированные зоны

Поведение, сознательно не являющееся частью контракта (не должно оформляться падающими тестами):

- Точный текст, формат и язык сообщений в лог (`console.info`/`console.error`) — при `debug=true` допустимо проверять лишь факт появления записей, не их дословное содержание.
- Порядок проверки независимых условий внутри конъюнкции (например, порядок §6 п.1–5) — наблюдаем только итоговый результат (включился/не включился свет), не порядок внутренних проверок.
- Точное поведение при значениях опций вне заявленных `minValue`/`maxValue`/типа (см. §16 п.10) — платформенный UI обычно не позволяет ввести такие значения через штатный редактор опций; поведение при их программной подаче (в обход UI) не определено этой спецификацией.
- Поведение при одновременных (в одном и том же «тике») событиях от разных устройств — порядок обработки нескольких одновременных изменений характеристик не специфицирован.
- Производительность, потребление памяти и внутренняя реализация подписки на события — не часть поведенческого контракта.
- Восстановление состояния между перезапусками хаба сверх того, что описано в §5/§16 п.2 — детальное поведение в момент рестарта не определено.
- Работа сценария при одновременном управлении несколькими независимыми его копиями на разных лампах — контракт описывает поведение одного экземпляра сценария, привязанного к одному сервису; взаимодействие между разными экземплярами (если они, например, настроены на одни и те же датчики) не специфицировано.
