## 1. Обзор

### 1.1 Назначение
Сценарий управляет ОДНОЙ характеристикой включения/выключения (`On`) выключателя (сервис `Switch`) по календарной дате «день.месяц» (без учёта года): в заданном пользователем периоде («зимнем») выключатель должен быть включён, вне периода — выключен. Типичное применение — сезонное отопление/кондиционирование/освещение. Пересчёт выполняется как по внешним событиям, так и автономно — каждую полночь (см. 2.1, 2.6). Записываемое значение может быть инвертировано, а имя сервиса — отражать текущий период (см. 2.2, 2.4).

### 1.2 Метаданные (справочно, не поведенческие)

|---|---|
| `name` | «❄️☀️ Зима/Лето» |

## 2. Логический сценарий — поведенческий контракт

### Модель привязки и параметров `trigger` (общая платформенная механика, нужна для понимания триггеров)
Логический сценарий Sprut.Hub привязывается пользователем в интерфейсе хаба к одному или нескольким конкретным аксессуарам (устройствам), обладающим нужным сервисом. У каждой такой привязки — собственный независимый набор значений опций и собственная независимая область переменных; код сценария один и тот же, но выполняется отдельно для каждой привязки со своими настройками. Функция `trigger(source, value, variables, options, context)`:
- `source` — обёртка над характеристикой `On` того выключателя, изменение которой вызвало срабатывание (либо, при срабатывании по `onStart`, — характеристика `On` привязанного аксессуара в её текущем состоянии); позволяет прочитать (`getValue`) и записать (`setValue`) значение, а также получить связанные сервис/аксессуар.
- `value` — новое значение этой характеристики на момент срабатывания (булево).
- `variables` — изменяемое хранилище данной привязки (см. 2.3).
- `options` — текущие значения опций данной привязки, только чтение (см. 2.2).
- `context` — служебная информация о причине срабатывания; сценарий не использует её наблюдаемым образом (итоговое поведение от неё не зависит, см. 2.4).

Сценарий не имеет опции выбора «целевого» устройства — он всегда читает и изменяет характеристику `On` именно того аксессуара, к которому привязан данный экземпляр логики / который вызвал срабатывание. Другого устройства сценарий не касается.

### 2.1 Триггеры выполнения

Срабатывание (`trigger`) происходит:
1. **При изменении значения характеристики `On` сервиса `Switch`** привязанного аксессуара — по любой причине (ручное переключение в приложении/на физической кнопке, другая автоматизация, облачная команда и т.д.). Срабатывает именно ИЗМЕНЕНИЕ значения; попытка установить характеристике то же значение, которое уже установлено, событием изменения не считается и срабатывания не вызывает.
2. **При старте (перезапуске) хаба** — поскольку `onStart = true`, для каждой привязки этого сценария выполняется дополнительное срабатывание с текущим значением характеристики `On`.
3. **При сохранении сценария** в интерфейсе хаба (например, после правки опций `startDate`/`endDate`) — по той же причине (`onStart = true`), также для каждой привязки, с текущим значением характеристики `On` на тот момент.
4. **Каждую полночь (00:00 по часам хаба)** — автономно, по Cron-расписанию, которое сценарий регистрирует сам при первом срабатывании привязки (см. 2.3, 2.6). Полуночный пересчёт производит тот же наблюдаемый эффект, что и обычное срабатывание: целевое состояние вычисляется заново по текущей календарной дате и текущим опциям и записывается в `On`. Это гарантирует переключение ровно в день границы диапазона без внешних событий.

Игнорируется (не вызывает `trigger` этого сценария):
- изменение любых характеристик, ОТЛИЧНЫХ от `On`, даже в пределах того же сервиса `Switch`;
- изменения на аксессуарах/сервисах, к которым данный экземпляр сценария не привязан в интерфейсе хаба (привязка не «все выключатели дома», а конкретно выбранные пользователем устройства);
- изменения характеристик на сервисах ДРУГОГО типа (не `Switch`), даже если они есть на том же физическом аксессуаре.

Результат срабатывания (изменение или неизменение состояния `On`) НЕ зависит от значения `value`, которое вызвало срабатывание, и НЕ зависит от того, каким было состояние `On` до срабатывания — целевое состояние вычисляется заново, исключительно из текущей календарной даты и текущих значений опций (см. 2.4). Платформенное замечание: если сценарий сам изменяет `On` этого же выключателя, это штатно для Sprut.Hub может вызвать повторное срабатывание; поскольку решение полностью детерминировано (не зависит от `value`/предыдущего состояния), повторный вызов вычислит тот же результат и дальнейших изменений не произведёт — самопроизвольного зацикливания быть не должно.

### 2.2 Опции (`options`)

| Поле | Тип | Значение по умолчанию | Формат / диапазон | Влияние на поведение |
|---|---|---|---|---|
| `startDate` | String | `"1.12"` | Дата «день.месяц» в одном из двух форматов, см. ниже | Начало («зимнего») периода, когда выключатель должен быть включён |
| `endDate` | String | `"1.03"` | Дата «день.месяц» в одном из двух форматов, см. ниже | Конец («зимнего») периода (включительно), когда выключатель должен быть включён |
| `changeServiceName` | Boolean | `false` | — | Включено: при каждом успешном срабатывании имя сервиса выключателя переписывается на имя текущего периода («Зима»/«Лето», правило — в 2.4). Выключено: имя сервиса не трогается вовсе |
| `invert` | Boolean | `false` | — | Включено: в характеристику `On` записывается инвертированное значение — внутри периода «выключено», вне периода «включено». Выключено: значение записывается как есть |

Отображаемые в UI названия: `changeServiceName` — «Менять имя сервиса» / «Change service name», `invert` — «Инвертировать» / «Invert». Кроме них в `info.options` объявлено информационное поле `desc` (`formType: "status"`, пустое значение) — блок справки в UI, на поведение не влияет и сценарием не читается.

Отображаемые в UI хаба названия опций: `startDate` — «Дата включения» / «Start date» (подсказка: «Дата включения выключателя (день.месяц или текст, например: 1.12 или 1 декабря)»); `endDate` — «Дата выключения» / «End date» (подсказка: «Дата выключения выключателя (день.месяц или текст, например: 1.03 или 1 марта)»). Ограничений длины строки (`maxLength`), а также `minValue`/`maxValue`/`step`/`values` не задано (не применимо, тип String без списка допустимых значений).

**Поддерживаемые форматы значения** (применяются независимо к `startDate` и `endDate`; можно использовать РАЗНЫЕ форматы для двух опций одновременно, например `startDate: "1.12"`, `endDate: "1 марта"` — это штатно):

- **Формат A («цифровой»)**: `<день>.<месяц>`, где `<день>` и `<месяц>` — по 1 или 2 цифры (ведущий ноль необязателен для любой из частей), разделитель — символ точки `.`. Числовое значение дня должно быть в диапазоне 1–31, месяца — 1–12. Примеры: `1.12`, `01.03`, `15.6`.
- **Формат B («текстовый»)**: `<день> <месяц-по-русски-в-родительном-падеже>` — день (1–2 цифры, значение 1–31), пробельный символ, название месяца на русском языке в родительном падеже. Примеры из README: `1 декабря`, `15 марта`, `10 сентября`, `1 ноября`, `28 февраля`. Ожидаемый полный список из 12 родительных форм: `января, февраля, марта, апреля, мая, июня, июля, августа, сентября, октября, ноября, декабря` (README дословно демонстрирует только 5 из них — декабря, марта, сентября, ноября, февраля; поддержка остальных 7 — разумное обобщение общего утверждения README, см. «Открытые вопросы»). Названия месяцев на других языках не поддерживаются.

**Правило валидации (общее для обеих опций).** Значение опции считается некорректным, если оно не соответствует НИ одному из двух форматов выше, включая: пустую строку; число дня вне 1–31; число месяца (формат A) вне 1–12; нераспознанное/иностранное слово на месте названия месяца (формат B). Особый случай — **число дня в диапазоне 1–31, но не существующее календарно для указанного месяца** (например, `31.04`, `30 февраля`) — по тексту README («Максимальный день в месяце: 31, корректность не проверяется для конкретных месяцев») это НЕ считается ошибкой конфигурации и должно приниматься как валидное значение (при этом его точная позиция при сравнении диапазонов не определена, см. раздел 4).

**Эффект некорректного значения.** Если некорректны `startDate`, ИЛИ `endDate`, ИЛИ обе сразу — сценарий не вычисляет диапазон и НЕ изменяет состояние характеристики `On` (она остаётся такой, какой была до срабатывания); ошибка фиксируется в логе (см. 2.7). Частичного применения (использовать только валидную из двух дат, откатиться к значению по умолчанию) не происходит — обе даты должны быть одновременно валидны, иначе решение не принимается вовсе. То же правило распространяется на любую иную непредвиденную ошибку при обработке срабатывания: она не «роняет» сценарий целиком — конкретное срабатывание завершается без изменения состояния и с записью ошибки в лог, а следующее срабатывание обрабатывается независимо и заново.

### 2.3 Переменные состояния (`variables`)

| Поле | Назначение |
|---|---|
| `midnightTask` | Ссылка на зарегистрированную Cron-задачу ежесуточной проверки даты (см. 2.1 п.4, 2.6). Заполняется при первом срабатывании привязки |
| `midnightOptionsKey` | Значения опций (`startDate`, `endDate`, `invert`, `changeServiceName`), с которыми задача была создана. Служит признаком того, что после правки опций задачу надо пересоздать |

Переменные — служебные: пользователь их не задаёт, и на вычисление целевого состояния конкретного срабатывания они не влияют. Наблюдаемое следствие: результат каждого срабатывания по-прежнему полностью независим от истории предыдущих срабатываний — при одинаковых входных условиях (текущая дата на момент срабатывания + текущие значения `startDate`/`endDate`) результат всегда одинаков, независимо от того, сколько раз и в каком порядке сценарий срабатывал до этого.

Единственный наблюдаемый эффект переменных — количество зарегистрированных Cron-задач: повторные срабатывания с тем же набором дат НЕ создают вторую задачу (задача одна на привязку), а срабатывание с изменёнными опциями заменяет задачу на новую — с актуальными значениями, снова ровно одну. После перезапуска хаба `variables` обнуляется платформой, и задача создаётся заново первым же срабатыванием по `onStart`.

### 2.4 Алгоритм определения нужного состояния выключателя

Целевое состояние вычисляется по трём величинам: текущая календарная дата (день + месяц; год не используется вообще — сценарий не различает, например, 2024-й и 2025-й год, только «какое сегодня число и месяц») и обе настроенные даты (`startDate`, `endDate`, после разбора по 2.2).

Даты сравниваются по их взаимному хронологическому порядку внутри условного года без указания конкретного года (месяц имеет больший вес, чем день внутри месяца: например, 5 марта «позже» 28 февраля, 1 апреля «позже» 31 марта). Правило (по README):

1. **Если `startDate` не позже `endDate`** в этом хронологическом порядке (диапазон «не пересекает год», например 1 июня – 1 сентября): выключатель должен быть ВКЛЮЧЁН, если текущая дата находится между `startDate` и `endDate` включительно с обеих сторон; иначе — ВЫКЛЮЧЕН.
2. **Если `startDate` позже `endDate`** в этом хронологическом порядке (диапазон «пересекает год», например 1 декабря – 1 марта): выключатель должен быть ВКЛЮЧЁН, если текущая дата ≥ `startDate` ИЛИ текущая дата ≤ `endDate` (обе границы включительно); иначе — ВЫКЛЮЧЕН.

**Инверсия.** Вычисленное по правилам выше значение «внутри периода» относится к ПЕРИОДУ, а не напрямую к характеристике. При `invert = false` в `On` записывается оно же; при `invert = true` — его отрицание (внутри периода `false`, вне периода `true`). Инверсия не влияет ни на определение периода, ни на имя сервиса.

После вычисления целевого состояния характеристика `On` устанавливается ровно в это значение — то есть после успешного (без ошибок) завершения срабатывания она ВСЕГДА равна вычисленному целевому состоянию (с учётом `invert`), независимо от того, каким было состояние до срабатывания.

**Имя сервиса (`changeServiceName = true`).** Имя определяется ТИПОМ диапазона, а не состоянием выключателя:

| Взаимный порядок дат | Текущая дата внутри периода | Текущая дата вне периода |
|---|---|---|
| `startDate` позже `endDate` (диапазон пересекает год, например 1.12 – 1.03) | `Зима` | `Лето` |
| `startDate` не позже `endDate` (диапазон внутри года, например 1.06 – 1.09) | `Лето` | `Зима` |

Имя перезаписывается при каждом успешном срабатывании (в том числе полуночном), поэтому заданное пользователем имя сервиса при включённой опции не сохраняется. При `changeServiceName = false` имя сервиса не изменяется никогда. Значение `invert` на имя не влияет. Если срабатывание завершилось ошибкой (2.2) либо не найдены сервис/характеристика (2.9), имя не изменяется.

### 2.5 Приоритеты правил при конфликтах

У сценария нет нескольких потенциально конфликтующих правил в обычном смысле — `startDate` и `endDate` совместно образуют единственный диапазон, и решение — результат одного сравнения. Порядок применения:
1. **Валидация.** Обе опции должны успешно разобраться по одному из двух форматов (2.2) — предварительное условие для всего остального. Невалидность любой из них прерывает обработку целиком; частичного/приоритетного применения одной валидной даты нет.
2. **Определение типа диапазона** («пересекает год» / «не пересекает год», см. 2.4) вычисляется автоматически из взаимного порядка `startDate`/`endDate` — пользователь не выбирает тип диапазона явно, это следствие введённых дат.
3. **Итоговое решение** не зависит от того, что именно вызвало срабатывание (значение `value`, служебный `context`), и не зависит от состояния `On` до срабатывания — только от текущей даты и текущих `startDate`/`endDate` (см. 2.4).
4. **Инверсия применяется последней** — уже к готовому решению «внутри/вне периода», и только к записываемому значению характеристики; на имя сервиса (`changeServiceName`) она не действует.

### 2.6 Тайминги

Сценарий не создаёт таймеров, интервалов и задержек, но регистрирует одно Cron-расписание на привязку — ежесуточное, на полночь (00:00:00). Задержек внутри срабатывания нет: вся обработка одного срабатывания выполняется непосредственно и сразу в момент вызова `trigger`: как только срабатывание обработано (без ошибок), состояние характеристики `On` уже равно вычисленному целевому значению — ожидания нет.

Момент, в который считывается «текущая дата» для алгоритма 2.4, — момент вызова `trigger` (а не момент, когда были сохранены/изменены опции, и не момент предыдущего срабатывания).

**Автономность посуточного переключения**: смена календарной даты сама по себе никакого события в хабе не порождает, поэтому автономность обеспечивается именно полуночной Cron-задачей (2.1 п.4). Если после последнего срабатывания долгое время не происходит ни ручного/иного изменения `On`, ни перезапуска хаба, ни пересохранения сценария, состояние всё равно будет пересчитано в ближайшую полночь — то есть в день границы диапазона выключатель переключится сам, максимальная задержка от момента пересечения границы до переключения равна нулю (граница диапазона и есть начало суток).

Задача существует, пока живёт привязка сценария в текущем запуске хаба. Если хаб был выключен в момент наступления полуночи дня границы, полуночного пересчёта в этот момент не происходит — состояние выставляется первым срабатыванием по `onStart` при старте хаба.

### 2.7 Логирование (вторичный наблюдаемый эффект)

По README сценарий ведёт журнал событий, доступный в интерфейсе хаба в разделе «Логи». Заявленное содержимое: текущая дата; настроенные даты включения/выключения; принимаемое решение (включить/выключить); изменения состояния выключателя. Раздел README «Устранение неполадок» прямо указывает проверять логи «на наличие ошибок» при некорректной дате или отсутствующем сервисе/характеристике — то есть ошибочные ситуации (2.2, 2.9) сопровождаются записью уровня ошибки.

Точный текст сообщений, формальный уровень (info/warn/error) как строгий enum и точное число записей за одно срабатывание README не фиксирует дословно — это НЕ часть контракта и не должно проверяться буквально. Если тестовая среда предоставляет доступ к перехваченным логам, разумно проверять только:
- при успешной (штатной) обработке — отсутствие записей уровня «ошибка»;
- при любой из ошибочных ситуаций (2.2, 2.9) — наличие как минимум одной записи уровня «ошибка».

Если доступа к логам нет — логирование можно не проверять вовсе: основной контракт сценария выражается через итоговое значение характеристики `On`, а не через логи.

### 2.8 Внешние зависимости

Единственная внешняя зависимость — системные часы хаба на момент срабатывания (см. 2.4, 2.6): используются только число дня и порядковый номер месяца, год игнорируется. Часовой пояс, в котором интерпретируется «текущая дата» (локальный часовой пояс хаба или UTC), README не уточняет (см. «Открытые вопросы», п.1) — при тестировании границ диапазона рекомендуется выбирать моменты времени с запасом от полуночи (например, середина дня), чтобы результат не зависел от этой неопределённости.

Сценарий НЕ обращается к внешним HTTP API, не использует данные о восходе/закате солнца или геопозиции, не читает и не пишет `GlobalVariables`/данные других сценариев. Единственное используемое расписание — собственная полуночная Cron-задача (2.1 п.4, 2.6), опирающаяся на те же системные часы хаба. Единственное устройство, с которым взаимодействует одно срабатывание, — тот же аксессуар/характеристика, что вызвала срабатывание (или, при `onStart`, аксессуар данной привязки); опции выбора иного устройства-цели нет.

### 2.9 Краевые случаи

**Валидность/формат дат** (см. также правило в 2.2):
- Пустая строка в `startDate` или `endDate` → не соответствует ни одному формату → ошибка конфигурации, состояние не меняется.
- День `0` или день `≥ 32` (числовой формат) → ошибка.
- Месяц `0` или месяц `≥ 13` (числовой формат) → ошибка.
- Нераспознанное или не русскоязычное слово на месте названия месяца (текстовый формат), например `"1 December"` → ошибка «неверное название месяца».
- Календарно несуществующий, но численно допустимый день месяца (например, `31.04`, `30 февраля`) → НЕ ошибка (принимается), но точная позиция такой даты в годовом порядке не специфицирована (раздел 4).
- `startDate` и `endDate` заданы в РАЗНЫХ форматах одновременно (один числовой, другой текстовый) → штатно поддерживается, оба разбираются независимо.

**Границы диапазона** (прямое следствие правила 2.4):
- Текущая дата ровно равна `startDate` → ВКЛ (граница включительно).
- Текущая дата ровно равна `endDate` → ВКЛ (граница включительно).
- Текущая дата на 1 календарный день раньше `startDate` (для диапазона, не пересекающего год) или на 1 день позже `endDate` → ВЫКЛ.
- `startDate` и `endDate` указывают на один и тот же день (например, оба `"1.06"`) → диапазон вырождается в один-единственный день: ВКЛ только в этот день года, ВЫКЛ во все остальные 364/365 дней.
- `startDate` хронологически на 1 календарный день ПОЗЖЕ `endDate` (например, `startDate = "2.06"`, `endDate = "1.06"`) → диапазон формально «пересекает год» и математически покрывает вообще ВСЕ дни года без исключения (условие «≥ start ИЛИ ≤ end» выполняется для любой даты) — выключатель включён ВСЕГДА, каждый день.

**Отсутствующее устройство/сервис/характеристика:**
- Аксессуар без сервиса `Switch` → состояние не меняется, ошибка в логе.
- Сервис `Switch` есть, но характеристика `On` отсутствует (в штатно сформированном устройстве не встречается, так как `On` — обязательная характеристика сервиса `Switch`, но сценарий защищается от этого явно, согласно README) → состояние не меняется, ошибка в логе.
- Устройство физически недоступно/офлайн на момент срабатывания → README отдельно эту ситуацию не описывает (см. «Открытые вопросы», п.9).

**Повторные срабатывания:**
- Повторные срабатывания подряд с одними и теми же (текущая дата, `startDate`, `endDate`) → идемпотентно: каждый раз вычисляется и выставляется одно и то же целевое состояние, независимо от количества повторов; количество зарегистрированных полуночных задач при этом остаётся равным одной (см. 2.3).
- Срабатывание после правки любой из опций (`startDate`, `endDate`, `invert`, `changeServiceName`) → полуночная задача заменяется на новую, работающую с новыми значениями; задач по-прежнему одна, «залипшего» расписания со старыми настройками не остаётся.
- Срабатывание уже при верном состоянии (`On` уже равен целевому значению) → характеристика остаётся равна тому же целевому значению (наблюдаемо неотличимо от «ничего не произошло»).

**Имя сервиса и инверсия:**
- `changeServiceName = false` (по умолчанию) → имя сервиса не меняется ни при каком срабатывании.
- `invert = true` при вырожденном диапазоне «один день» (`startDate` = `endDate`) → выключатель включён все дни года, кроме этого одного.
- `invert = true` при диапазоне, покрывающем весь год (`startDate` на день позже `endDate`) → выключатель выключен всегда.

**Несколько привязок:** сценарий может быть одновременно привязан к нескольким разным выключателям, каждый — со своими независимыми `startDate`/`endDate`; поведение одной привязки не влияет на другую.

**Взаимодействие с другими сценариями/автоматизациями**, одновременно управляющими той же характеристикой `On`, этим контрактом не описывается: WinterSummer гарантирует итоговое состояние только непосредственно по результатам собственного срабатывания, без учёта гонок с другими источниками записи.

## 3. Открытые вопросы

1. **Часовой пояс «текущей даты».** README не указывает, читается ли дата хаба в его локальном часовом поясе или в UTC. Критично для поведения вблизи полуночи дня границы диапазона. Пользователь, вероятно, ожидал бы локального времени хаба/дома.
2. **Реакция на некорректное значение даты.** README описывает только факт логирования ошибки, но явно не говорит, остаётся ли выключатель в прежнем состоянии, принудительно выключается, или используется значение по умолчанию. В спецификацию включён вариант «состояние не меняется» как наиболее безопасный и ожидаемый пользователем.
3. **Обработка 29 февраля / високосных годов.** README нигде не упоминает високосные годы — не специфицировано поведение при текущей дате 29 февраля или при границе диапазона на 29 февраля.
4. **Позиция календарно несуществующих дат** (например, «31 апреля», «30 февраля») в годовом порядке сравнения. README прямо разрешает такие значения без ошибки, но не определяет их фактическую позицию при сравнении с другими датами.
5. ~~**Автономность посуточного переключения.**~~ ЗАКРЫТ в версии 1.1: добавлена полуночная Cron-задача, README описывает её явно (см. 2.1 п.4, 2.6). Открытым остаётся смежный вопрос — поведение при выключенном на момент полуночи хабе описано только как «пересчёт при старте».
6. **Регистрозависимость и пробелы в текстовом формате.** Не указана чувствительность к регистру названия месяца (например, «Декабря» vs «декабря») и точная гибкость пробелов между числом дня и названием месяца.
7. **Полный список поддерживаемых названий месяцев.** README дословно демонстрирует лишь 5 из 12 родительных форм (декабря, марта, сентября, ноября, февраля); поддержка остальных 7 — разумное обобщение, не подтверждённое явным примером.
8. **Частично валидная пара дат.** README не описывает явно поведение, если валидна только ОДНА из двух дат. Принят вариант «обе даты должны быть валидны одновременно, иначе состояние не меняется», без частичного применения одной валидной границы.
9. **Офлайн/недоступное устройство.** README не уточняет, отличается ли (и как) поведение сценария, если целевой аксессуар физически недоступен, от поведения с доступным устройством.

## 4. Неспецифицированные зоны

Поведение из этого раздела сознательно не фиксируется как обязательный контракт — по нему не следует писать проверяющие тесты с жёстким ожиданием конкретного результата, только фиксировать наблюдения:

- Точная относительная позиция в годовом порядке для календарно несуществующих, но численно допустимых дат (`31.04`, `30 февраля`, `31.06` и т.п.) при сравнении диапазонов.
- Точное поведение при текущей дате 29 февраля (в високосный год), когда граница диапазона расположена рядом (например, `endDate = "28 февраля"` или `startDate = "29 февраля"`).
- Часовой пояс, используемый для определения «текущей даты» (локальный/UTC), и поведение ровно в момент смены календарного дня.
- Регистрозависимость названия месяца в текстовом формате и точная гибкость пробельных символов между числом дня и названием месяца.
- Точный текст, уровень и количество записей в логе за одно срабатывание (кроме факта наличия минимум одной записи уровня «ошибка» при ошибочных ситуациях, см. 2.7).
- Поведение при офлайн/физически недоступном целевом устройстве.
- Поведение при одновременном изменении характеристики `On` этим сценарием и сторонними сценариями/автоматизациями (гонки записи).
- Совместимость с сервисами/аксессуарами, формально не проходящими фильтр `sourceServices`/`sourceCharacteristics` (сценарий рассчитан исключительно на сервис `Switch` / характеристику `On` — поведение при попытке иного использования не определено и не тестируется).
