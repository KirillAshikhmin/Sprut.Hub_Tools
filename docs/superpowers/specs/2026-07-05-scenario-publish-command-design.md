# Команда `publish` — подготовка сценария к публикации

**Дата:** 2026-07-05
**Статус:** дизайн согласован, ожидает ревизии спеки

## 1. Цель и контекст

Автоматизировать подготовку сценария Sprut.Hub к публикации одной командой. На входе — папка сценария с исходниками `source/*.js`. На выходе — сгенерированные `.json`-экспорты (для импорта в хаб), прогнанные тесты и набор проверок качества, которые не дают опубликовать заведомо сломанный или недооформленный сценарий.

Команда поддерживает:
- **логические** сценарии (есть `info` + `trigger`/`compute`);
- **глобальные** сценарии (библиотека функций, без `info`);
- **шаблонные** сценарии TEMPLATE (есть `update()`, без `info`);
- **многофайловые** сценарии (напр. `CircadianLight`: один логический + несколько глобальных + вспомогательные логические).

### 1.1. Изменение политики репозитория (важно)

Текущий `CLAUDE.md` содержит правило: *«.json-файлы сценариев — экспорты из UI Sprut.Hub, пользователь обновляет их сам, не создавать и не править»*.

Эта команда **намеренно разворачивает** это правило: источником правды становится `source/*.js`, а `.json` **генерируются** командой `publish`. Часть работы — обновить `CLAUDE.md`: заменить запрет на «JSON генерируются из `source/` командой `publish`; вручную не редактировать» и описать манифест и команду.

Обоснование, что это безопасно: формат экспорта тривиально выводится из исходника. Пример `VirtualThermostat/VirtualThermostat.json`:

```json
{ "scenarioTemplate": { "name", "desc", "active", "onStart", "sync", "data": "<весь текст .js>", "type": "LOGIC" } }
```

Поле `data` — дословный текст исходника; метаданные логических сценариев целиком лежат в блоке `info`. Более того, текущие `.json` уже устарели относительно `source/` (в `CircadianLight/Конвертер температуры в цвет.json` в `data` старый код с опечаткой «нысыщенность» и без блока валидации, который уже есть в исходнике) — это подтверждает, что source давно стал источником правды.

## 2. Архитектура и размещение

Команда — **подкоманда существующего CLI** `ScenarioSimulator`, а не отдельная утилита: в `packages/core` уже есть `ConfigLoader`, `Validator` (AST-проверка ES5+), `Runner` (тесты) и зависимость `acorn`. Дублировать это нельзя (DRY).

- **Чистая логика** → `packages/core/src/publish/`:
  - `detectType.ts` — определение типа сценария по AST/содержимому.
  - `parseInfo.ts` — статическое извлечение полей `info` через `acorn`.
  - `generateJson.ts` — сборка объекта `scenarioTemplate` и сериализация.
  - `manifest.ts` — чтение/автогенерация `publish.json`.
  - `changelog.ts` — проверка раздела «История изменений» в README.
  - `zip.ts` — минимальный ZIP-writer без зависимостей.
  - `publish.ts` — оркестратор конвейера (объединяет всё выше + `Validator` + `Runner`), возвращает структурированный результат.
- **Тонкая CLI-обёртка** → `packages/cli/src/commands/publish.ts`, регистрируется в `packages/cli/bin/scenario-sim.ts` рядом с `run`/`validate`/…
- **Корневой алиас** → исполняемый `./publish` (bash) в корне репозитория:

  ```bash
  #!/usr/bin/env bash
  set -euo pipefail
  DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
  exec bun "$DIR/ScenarioSimulator/packages/cli/bin/scenario-sim.ts" publish "$@" --root "$DIR"
  ```

  Позволяет запускать из корня: `./publish CircadianLight`. Windows-обёртка (`.cmd`) — вне рамок v1 (разработка ведётся на macOS); там доступна прямая команда `bun run cli publish <Name> --root ..` из папки симулятора.

**Требования окружения:** установленный `bun` и однократный `bun install` в `ScenarioSimulator/`.

## 3. Манифест `publish.json`

Лежит в корне папки сценария (рядом с `README.md`). Единственный явный источник для публикации; дополняет `.tests/config.json` (тот — для симулятора).

```jsonc
{
  "$schema": "../ScenarioSimulator/schemas/publish.schema.json",
  // "version": "7.0",              // опц. fallback; ЗДЕСЬ не нужен — версия берётся из primary (Логический.js).
                                    //   Задаётся только для папок БЕЗ логических файлов (чисто глобальных).
  "archive": "CircadianLight.zip",  // опц.: имя zip ИЛИ true (тогда <Папка>.zip). Нет поля — архив не собирается
  "files": [
    { "source": "source/Логический.js", "primary": true },        // LOGIC: метаданные из info
    { "source": "source/Отключение циркадного освещения.js" },     // второй LOGIC (не primary)
    { "source": "source/Глобальный.js",
      "json": "Циркадное освещение. Глобальный.json",
      "name": "Циркадное освещение. Глобальный",
      "archive": true },
    { "source": "source/Глобальный. Параметры.js",
      "json": "Циркадное освещение. Глобальный. Параметры.json",
      "name": "Циркадное освещение. Глобальный. Параметры",
      "archive": true },
    { "source": "source/Конвертер температуры в цвет.js" }
  ]
}
```

### 3.1. Поля записи `files[]`

| Поле | Обяз. | Смысл / значение по умолчанию |
|---|---|---|
| `source` | да | Путь к `.js` относительно папки сценария. |
| `json` | нет | Имя выходного JSON. **По умолчанию `<Имя папки>.json`.** Для многофайловых — указывать явно. |
| `type` | нет | `LOGIC`/`GLOBAL`/`TEMPLATE`. По умолчанию — автоопределение по содержимому. |
| `name` | нет | LOGIC/TEMPLATE — из `info.name` (переопределение не нужно). GLOBAL — из существующего JSON, иначе имя папки. |
| `desc` | нет | LOGIC — из `info.description`. GLOBAL — из существующего JSON, иначе `""`. |
| `active` | нет | По умолчанию `true` (или из существующего JSON для GLOBAL). |
| `sync` | нет | По умолчанию `false`. |
| `primary` | нет | Помечает основной логический файл папки — его `info.version` берётся для changelog-проверки. |
| `archive` | нет | `true` — включить этот JSON в zip. |

### 3.2. Автогенерация манифеста

Если `publish.json` отсутствует — команда его создаёт и продолжает работу (сообщив пользователю, чтобы он проверил результат):

1. Перечислить исходники: объединение массивов `globals`+`logic` из всех `.tests/*config.json` папки; при отсутствии конфигов — `source/*.js`.
2. Для каждого определить тип (см. §4).
3. Привязать к существующему JSON в папке:
   - **LOGIC/TEMPLATE** — по совпадению `info.name` с полем `name` внутри JSON.
   - **GLOBAL** — по наибольшему совпадению содержимого исходника с полем `data` существующих GLOBAL-JSON (bootstrap-эвристика). Если нет кандидата — `json = <Имя папки>.json`, `name = <Имя папки>`.
4. Если в папке есть `*.zip` — подставить его имя в `archive` и пометить `archive:true` у файлов, чьи JSON реально присутствуют внутри архива (имена читаются из zip).
5. Записать `publish.json`.

## 4. Определение типа сценария

**По содержимому исходника** (НЕ по `config.json`: там `Конвертер температуры в цвет.js` лежит в `globals`, хотя это LOGIC — массивы `globals`/`logic` описывают загрузку для симулятора, а не тип публикации):

- верхнеуровневое присваивание `info = {…}` (или `var info = …`) **и** `function trigger`/`function compute` → **LOGIC**;
- `function update(` без `info` → **TEMPLATE**;
- иначе → **GLOBAL**.

## 5. Генерация JSON

Поле → источник:

| Поле JSON | LOGIC / TEMPLATE | GLOBAL |
|---|---|---|
| `data` | дословный текст `.js` | дословный текст `.js` |
| `name` | `info.name` | манифест → существующий JSON → имя папки |
| `desc` | `info.description` | манифест → существующий JSON → `""` |
| `active` | `info.active`, деф. `true` | существующий JSON, деф. `true` |
| `onStart` | `info.onStart`, **деф. `true`** | **не эмитится** |
| `sync` | `info.sync`, деф. `false` | существующий JSON, деф. `false` |
| `type` | `LOGIC` / `TEMPLATE` | `GLOBAL` |

- Скалярные поля `info` (`name`, `description`, `onStart`, `active`, `sync`, `version`) извлекаются **статически через acorn** — на практике это всегда строковые/булевы литералы, исполнять код сценария не нужно. Если поле задано не-литералом — ошибка с понятным сообщением.
- Для LOGIC `info` — источник правды: `name/desc/onStart/active/sync` берутся из него (с дефолтами), а НЕ из существующего JSON.
- Для GLOBAL `info` нет: `name/desc/active/sync` берутся из манифеста → существующего JSON → дефолтов. Поле `onStart` у глобальных не эмитится.
- Сериализация — `JSON.stringify(obj, null, 2)`. Порядок ключей: `name, desc, active, onStart(только LOGIC/TEMPLATE), sync, data, type` — чтобы минимизировать diff с текущими файлами.

## 6. Версия и проверка changelog

### 6.1. Источник версии папки

Приоритет (логический сценарий — источник правды):

1. Есть логические/TEMPLATE файлы:
   - ровно один → его `info.version`;
   - несколько → файл с `primary: true` → его версия; иначе, если версии всех совпадают → эта версия; иначе → **ошибка** «неоднозначная версия: пометьте `primary` или задайте `manifest.version`».
2. Логических файлов нет → `manifest.version` (fallback).
3. Ни того, ни другого → changelog-проверка неприменима, пропускается с пометкой.

### 6.2. Проверка

В README ищется раздел «История изменений» (терпимо к формату заголовков: у `VirtualThermostat` — `### Версия 3.1`, у `CircadianLight` — `## 6.0`; ищем номер версии в заголовках раздела, а не точный текст). Если записи с текущей версией нет — **ошибка** (по умолчанию). Флаг `--allow-missing-changelog` понижает до предупреждения.

> Проверка сразу ловит реальный баг: у `CircadianLight` `info.version = "7.0"`, а верхняя запись changelog — `## 6.0`.

## 7. Конвейер `publish`

**Команда НЕ прерывается на первой ошибке.** Сначала выполняются ВСЕ проверки, результаты аккумулируются; запись файлов происходит, только если ошибок нет.

Обозначения: ❗ = ошибка (блокирует генерацию), ⚠️ = предупреждение (не блокирует).

### Фаза 1 — проверки (без записи на диск)

Выполняются все пункты; каждый обёрнут так, что сбой одного не мешает остальным (исключение конвертируется в ❗-запись отчёта):

1. **Манифест** — загрузить; если файла нет — вывести в памяти (§3.2), пометив, что он будет создан в фазе 2. ❗ при неразрешимых ссылках (`source` не существует).
2. ❗ **Синтаксис + неподдерживаемые конструкции** — `Validator({mode:"es5+"})` по каждому исходнику. ParseError + запрещённые в Nashorn узлы: классы, `import`/`export`, `async`/`await`, генераторы/`yield`, spread/rest, деструктуризация, optional chaining, `MetaProperty`.
3. ❗ **Метаданные `info`** (LOGIC/TEMPLATE): `name`/`description`/`version` присутствуют и являются литералами; при заданном в манифесте `name` — сверка с `info.name`.
4. ❗ **Changelog** (§6): запись с текущей версией существует. `--allow-missing-changelog` → ⚠️.
5. ❗ **Коллизии** (два `source` → один `json`) / ⚠️ **сироты** (JSON в папке без ссылки из манифеста).
6. ⚠️ **Дрейф версии**: собранный в памяти `data` отличается от закоммиченного JSON, но `version` не менялась и в changelog нет новой записи → «код изменён, а версию не подняли».
7. ❗ **Тесты** — `Runner` по всем конфигам папки (тесты гоняются по исходникам, запись JSON для этого не нужна).

### Фаза 2 — решение

- **Есть хотя бы одна ❗** → напечатать ВСЕ собранные ошибки и предупреждения единым понятным отчётом (сгруппировано по файлу/проверке, с путём и строкой), **ничего не писать** на диск, код возврата ≠ 0.
- **Ошибок нет** → сгенерировать JSON (§5) в папку, записать `publish.json` (если его не было), собрать архив (§8), напечатать «всё ок» + все ⚠️, код возврата 0.

### 7.1. Флаги

- `--check` / `--dry-run` — фаза 1 (все проверки) + показать отчёт и diff генерации, **без записи** JSON/zip даже при чистом прогоне.
- `--init` — только (пере)создать манифест.
- `--no-tests` — пропустить прогон тестов (не рекомендуется).
- `--allow-missing-changelog` — changelog-провал → предупреждение.

## 8. Архив (zip)

Собственный минимальный ZIP-writer на `Bun.deflateSync` в `core/src/publish/zip.ts` — **без зависимостей, кросс-платформенно, без мусора `__MACOSX`** (в отличие от текущего `CircadianLight.zip`, собранного Finder). Кладёт в архив JSON'ы, помеченные `archive:true` (или все, если `archive` задан как просто `true`). Пишет `<...>.zip` в корень папки сценария.

## 9. Обработка ошибок

- Все проверки собирают структурированные результаты (`{severity, code, message, file?, line?}`), а не бросают исключения по месту — оркестратор печатает единый отчёт и выставляет код возврата.
- **Запись на диск — только если в фазе 1 ноль ❗** (⚠️ не блокируют). При наличии ошибок ни один файл не создаётся/не перезаписывается.
- Отсутствие исходника из манифеста, не-литерал в `info`, отсутствие блока `info` у LOGIC — понятные сообщения с путём/строкой.
- `--check` никогда не пишет на диск.

## 10. Тестирование

Юнит-тесты в `packages/core` (`bun test packages/core`):

- `detectType`: LOGIC/GLOBAL/TEMPLATE на реальных исходниках репозитория.
- `parseInfo`: извлечение полей + дефолты (`onStart` деф. `true`) + ошибка на не-литерале.
- `generateJson`: golden-сравнение с эталонным `scenarioTemplate` (в т.ч. отсутствие `onStart` у GLOBAL, порядок ключей).
- `manifest`: автогенерация и привязка к существующим JSON (LOGIC по имени, GLOBAL по содержимому).
- `changelog`: разные форматы заголовков; выбор версии (один/несколько логических/`primary`/fallback).
- `zip`: корректная структура архива, отсутствие `__MACOSX`, распаковывается системным `unzip`.
- Коллизии/сироты: срабатывание правил.

Ручная проверка: `./publish CircadianLight --check` и `./publish VirtualThermostat`.

## 11. Вне рамок v1 (YAGNI)

- Денилист ES6+ **рантайм-API** (`Object.assign`, `Promise`, `Symbol`, `Reflect`, `Proxy`) — то, что AST-валидатор не ловит. Легко добавить позже отдельной проверкой.
- Линт чтения `info.` в рантайме (CLAUDE.md это запрещает).
- Windows-обёртка `.cmd` для корневого алиаса.
- Кросс-файловая проверка существования вызываемых `global.*` функций.

## 12. Результат работы (deliverables)

1. `packages/core/src/publish/*` + экспорт из `core/src/index.ts`.
2. `packages/cli/src/commands/publish.ts` + регистрация в `bin/scenario-sim.ts`.
3. `ScenarioSimulator/schemas/publish.schema.json`.
4. Корневой `./publish` (исполняемый).
5. Юнит-тесты в `packages/core`.
6. Обновлённый `CLAUDE.md` (политика JSON + описание команды и манифеста).
7. (Опц., по согласованию) сгенерированные `publish.json` и обновлённые `.json` для существующих сценариев.
